# 0.140 TTS 修复（第七轮）：独立的音频 API Key（豆包语音 Key 与方舟 Key 分离）

> 状态：**用户已豁免审批**（「直接修改 不需要 审批了」），直接实施。
> 前置：0.139 已实施——端点、协议、音色全部正确，真机验证 **HTTP 404 → 401**（端点已通，服务器开始正常应答）。
> 根因：**豆包语音（openspeech）与方舟（ark）是两套独立体系，Key 也相互独立**——0.139 拿方舟 Key 填 X-Api-Key，服务器不认，报 `45000010 Invalid X-Api-Key`。
> 决定性证据：用户 2026-10-02 提供豆包语音控制台截图（「语音合成2.0」已开通、20,000 字免费额度、APP ID 4202991133）+ 已在豆包语音控制台新建独立 API Key（「新的 api 我也建好了」）。

## 一、401 之谜的答案

| 问题 | 答案 |
|---|---|
| 为什么报 Invalid X-Api-Key | `X-Api-Key` 要的是**豆包语音控制台**新建的 Key，不是方舟 Key（ark- 开头）——两套体系 Key 相互独立、不通用 |
| 用户已做什么 | 豆包语音控制台已开通「语音合成2.0」（20,000 字免费额度），并新建了独立 API Key |
| App 缺什么 | 之前 TTS 一直借用对话的方舟 Key（config.apiKey），**没有独立的音频 Key 字段**——这就是 401 的根因 |

六轮进展链：0.134/0.137 敲错门（404）→ 0.139 敲对门但拿错钥匙（401）→ 0.140 换对钥匙。

## 二、改动点明细（3 文件）

### ① ChatModel.ets：ApiConfig 新增 audioKey 字段
- `@Trace audioKey: string = '';`（默认空，用户在设置页填入豆包语音 Key）
- PersistenceV2 整对象持久化：新字段自动保存；旧持久化数据无此字段，自动用默认值空串，不报错

### ② SettingsPage.ets：音频设置区新增「音频 API Key」输入框（5 处）
- `@Local editAudioKey` 编辑副本 + aboutToAppear 初始化 + hasUnsavedChanges 比对 + 保存按钮写回
- 输入框位置：音频模型区块之前（与对话区 Key 在最前的风格一致）
- 提示文字：说明这是豆包语音控制台的 Key，与对话用的方舟 Key 相互独立、不通用

### ③ ApiClient.ets：synthesizeTTS 换用 audioKey + 空值检查
- 请求头 `X-Api-Key: config.apiKey` → `config.audioKey`
- 新增空值检查：audioKey 为空时**不发起请求**，直接报错提示「请在设置页填入音频 API Key」（避免拿空 Key 撞服务器得到模糊 401，让用户白猜）

### ④ SettingsPage.ets：Scroll 滚动容器（真机实测发现）
- 现象：0.140 新增音频 Key 区块后设置页内容超出单屏，**页面不能下滑、保存按钮被推出屏幕外点不到**（用户真机实测「不能往下划，不能点击保存」）
- 修复：Column 外包一层 Scroll（内容高度自适应 + 垂直滚动 + 边缘弹性效果），padding 移至内层 Column，背景色留在 Scroll 层
- 教训：每次给设置页加区块总高度都在增长，长页面必须配滚动容器——0.133/0.139 加区块时已接近临界，0.140 压垮
