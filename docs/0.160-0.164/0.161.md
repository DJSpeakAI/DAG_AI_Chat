## 一、需求（用户原意）

在**单词库页面右上角、加号（+）左边**增加一个**设置按钮（⚙）**，点开设置弹窗，提供「学习数量」选项：

| 选项 | 说明 |
|---|---|
| 1 | 每次复习展示 1 条词条 |
| 2（默认） | 每次复习展示 2 条词条（原始行为） |
| 自由输入 | 用户输入 1~20 任意整数，确定生效 |

学习数量在**两个地方**生效（展示对应数量的词条）：

1. **AI 回复的时候** —— AI 回复气泡底部的生词复习区（📚 词条）
2. **知识卡片制作的时候** —— 知识卡片提炼等待页（编辑弹窗）内的复习区

## 二、实施改动

- 新增 `LearnCountStore`（@ObservedV2）：`@Trace learnCount: number = 2`（默认 2，合法范围 1~20）
- 新增 `connectLearnCount()`：PersistenceV2 独立全新 key `learn-count-v1`（与 AiPreference 同模式，全新 key 无旧快照缺字段坑，跨重启保存）

### 改动 2：单词库页面（WordBankPage.ets）

- **顶栏**：Blank 与 + 按钮之间插入 ⚙ 按钮（普通/多选两种模式均可见）
- **设置弹窗**（learnSettingsDialog @Builder，与编辑弹窗同款样式）：
  - 标题「学习数量设置」+ 说明文字（两处生效位置）

  - 非法输入（非整数/越界）显示红色提示「请输入 1~20 的整数」，不关闭弹窗
  - 打开弹窗时：当前值为自定义值（>2）则预填输入框，否则留空
- **挂载**：build 尾部弹窗堆叠区 + onBackPressed 返回键关闭（与既有三弹窗同模式）

### 改动 3：两处复习区消费设置（ChatPage.ets）

  - `pickRandomWords(this.wordBank, this.learnCountStore.learnCount)` —— 词条数由设置驱动
  - 缓存 version 升级为双维度编码 `词库长度 * 100 + 学习数量`（count≤20 无碰撞）——改数量后旧消息重抽新数量词条，改词库长度同样重抽（原行为保留）
- **提炼等待页复习区**（refreshEditReview）：
  - `pickRandomWords(this.wordBank, this.learnCountStore.learnCount)` —— 同一设置实例（PersistenceV2 单例，单词库改完全局即时生效）
  - 知识卡片固定 1 张不变（需求只涉及词条数量）

## 0.161.3 — API Key 外置（rawfile/config.json + .gitignore，源码可安全上传 GitHub）

### 需求（用户原话）

「做一个 ignore 忽略这个文件，我现在有 api key 然后，github 上传不了」——此前 Key 硬编码在 ChatModel.ets（0.160.1 内置），源码推上 GitHub 即泄漏，需要把 Key 挪到被 git 忽略的本地配置文件。

### 实施

**1. 新建 `entry/src/main/resources/rawfile/config.json`**（含 apiKey + audioKey，从源码原样挪入；**.gitignore 已忽略，绝不入库**，`git check-ignore` 已验证生效）

**2. ChatModel.ets**：
- `ApiConfig` 默认值：`apiKey` / `audioKey` 硬编码 → **空串**（源码不再含任何密钥）
- 新增 `BuiltinConfig` 接口 + `loadBuiltinApiConfig(context)`：`resourceManager.getRawFileContentSync('config.json')` → `util.TextDecoder` 解码 → `JSON.parse` → 填充持久化配置**空位**（用户设置页自定义过的 Key 优先，不被覆盖）；文件缺失/解析异常静默跳过（clone 后未放本地配置的场景，走设置页自填）

**3. EntryAbility.ets**：`onWindowStageCreate` 里 **loadContent 之前**调 `loadBuiltinApiConfig(this.context)`——早于所有页面组件 connect ApiConfig，保证填充先于读取

**4. .gitignore**：新增 `entry/src/main/resources/rawfile/config.json`；顺手重建该文件（原文件尾部混入 UTF-16 脏字节导致工具读不了，规则全部保留）

**5. 版本号**：v0.161.2 → v0.161.3

### ⚠️ 两条重要边界（必须知晓）

1. **config.json 会打进 HAP**：自己装机测试没问题；但**上架 / 公开分发 HAP 前仍须移除**（原「上架前删除内置 Key」约束不变，只是位置从源码挪到了 rawfile）
2. **git 历史处理**：含 Key 的提交 `1c338af`（0.161.1）**尚未推送**（本地 ahead 1，远程停在 0.149），且全历史仅此一个提交引入过 Key——推送前必须把它重写掉，否则历史里仍能翻到 Key。推荐操作（在项目根目录）：

   git commit --amend -m "0.161 学习数量/知识卡片数量设置 + API Key 外置"

   （amend 会把本次改动并入 1c338af 并生成干净的新提交，历史从未出现 Key）

## 0.161.4 — 推送被 GitHub Push Protection 拦截，历史重写修复

### 事件

用户在未先执行 0.161.3 章节所述 amend 的情况下直接 push，被 **GitHub Push Protection（GH013）** 拦截：

- 检测到 **VolcEngine Ark API Key** 位于提交 `1c338af`（`entry/src/main/ets/common/ChatModel.ets:192`）
- 推送被整体拒绝，**远程 main 仍停在 fd0666e（0.149），Key 未进入 GitHub，未泄露**

### 根因与方案修正

0.161.3 时点的 amend 方案已失效：用户此后把 0.161.2/0.161.3 改动提交成了新提交 `42ee261`，历史变为 `fd0666e → 1c338af(含Key) → 42ee261`——含 Key 提交卡在历史**中间**，amend 只能改 HEAD，够不着 `1c338af`。

正确方案（**reset --soft 合并重写**，本地操作）：

```
git reset --soft fd0666e     # HEAD 移回远程位置，两个提交的全部改动进暂存区
git add -A                    # 并入 0.161.4 版本号等剩余改动
git commit -m "0.161 学习数量/知识卡片数量设置 + API Key 外置 + 推送修复"
git push                      # 远程只收到一个干净提交，历史从未出现 Key
```

安全性依据：soft reset 不动工作区内容；当前代码（0.161.3 完成后）经 `git grep` 验证 `entry/src` 中两个 Key **零残留**，故合并后的新提交必然干净。该提交从未推送成功过，普通 push 即可，无需 force。

### ⚠️ 重要提醒

- GitHub 报错中的 `unblock-secret` 链接**绝对不要点**——那是「允许该 Key 进入仓库」的豁免通道，点击即等于把 Key 公开
- Key 仅经过 GitHub 扫描系统（被拒绝、未入库）；如仍介意可在火山方舟控制台轮换 Key，不轮换也可继续使用

v0.161.3 → v0.161.4
