## 二、✅ 已闭环：chat 页秒表不显示（2026-10-03 设备实测通过）

### 现象（历史）
AI 流式回复期间，占位文字后应显示蓝色 `⏱ XX秒` 每秒跳动——实际不显示。两台设备实测均无。

### 排查链（三轮递进，勿重查）
1. **版本旧**——排除（v0.150 设备显示实证）
2. **代码未进包**——排除（HAP 字节码实证）
3. **渲染条件不满足**——排除（isLoading/streamingMessageId/content 占位均实证正确）
4. **布局挤出**——排除（非右对齐、无宽度约束）
5. **if 分支切换不可靠**——第一轮方案：占位行/操作行秒表改「始终渲染 + visibility(isLoading && streamingMessageId...)」→ **装机实测证伪**：控件树无 ⏱ 节点，占位文字 clickable:true 走的仍是 Markdown 通道（bindSelectionMenu 特征）

### 最终根因（实测实锤）
ForEach item 创建于 messages 赋值瞬间（同步 diff），item 内 **visibility/分支的初始求值决定组件是否在渲染树上**——初始 `None`/`false` 的组件被移出渲染树后，**后续 @Local/@Trace 通知永不到达**（第一轮 visibility 绑定的 isLoading 在 item 创建瞬间尚未赋值 → 初始 None → 永远回不来）。朗读喇叭三态正常是因为它**一直在树上**（初始 Visible，仅内容切换）。

### 最终修复方案（isStreaming 模式，实测通过）
**原则：ForEach item 内依赖状态的组件，初始求值必须 Visible（在树上），后续靠 @Trace 通知切 None。**
1. **ChatModel.ets**：ChatMessage 加 `@Trace isStreaming: boolean = false`（字段级默认值，旧快照反序列化自动 false）
2. **sendMessage**：`aiMsg.isStreaming = true` **必须在 messages 赋值前**（item 创建时初始即 true → Visible）
3. **regenerateMessage**：`msg.isStreaming = true`（复用已有 item 在树上，通知可靠）
4. **onDone/onError**（双入口共 4 处）：`isStreaming = false`（@Trace 通知在树上的秒表切 None）
5. **占位行**：visibility 只绑 `@Trace content`（item 创建时 content=占位值 → 初始 Visible ✓），秒表移出
6. **操作行秒表**：`Text(⏱ 秒).visibility(msg.isStreaming ? Visible : None)`（初始 true ✓）

### 设备实测实证（畅享 90 Pro Max，2026-10-03 14:34-14:40）
- 流式期间控件树：`🔄 (790,2132) + ⏱ 6秒 (874,2132) + 🔈 (1005,2132)` —— 秒表出现在操作行，6 秒 = 计时器累加 + @Local 通知生效
- 回复完成后：⏱ 消失、token 统计「输入 844 · 输出 1467」出现、发送按钮恢复 —— isStreaming=false 切 None 生效
- 内置 API key 两次请求均成功（卸载重装后默认值生效）

### 注意
- 对话页秒表**不加 180s 超时**（区别于提炼弹窗——长回复可超 3 分钟，超时中断破坏回复）
- 设备无线调试端口会变（手机 192.168.2.9、平板 192.168.2.16），连不上先让用户查开发者选项→无线调试端口
- **ArkUI V2 经验（重要）**：ForEach item 内禁用「初始求值为 None/false 的 visibility/if」控制显隐——必须保证初始 Visible 在树上，用 @Trace 字段驱动后续切换
- **真机测试统一用平板**（MatePad 11.5 S，用户常开）；手机用户日常使用勿动（2026-10-03 用户指定）

## 三、✅ 0.160.1 三次修复：占位文字重复显示两次（2026-10-03 用户截图报告）

### 现象
深度思考期间「AI 正在深度思考中...」在气泡内显示**两次**；操作行秒表 ⏱ 3秒 正常（isStreaming 方案生效）。

### 根因
二次修复后占位行 Row（绑 content，正常显示占位文字一次）与 Markdown Column（一轮遗留的反向 visibility 绑 @Local isLoading/streamingMessageId）双通道并存——**item 创建同帧内的 @Local 变化驱动不了 item 内 visibility**（742 赋值创建 item 时 isLoading=false → Markdown 初始 Visible；747/748 同步执行 isLoading=true 的通知未生效）→ Markdown 恒 Visible 再渲染占位文字一次 → 重复。

### 修复（回归最简结构）
1. **删除占位行 Row**——秒表已在操作行（isStreaming），占位行存在意义消失
2. **删除 Markdown Column 反向 visibility**——占位文字与正文统一走 Markdown 通道渲染（原始行为，content @Trace 驱动，一直可靠）

### 结论（ArkUI V2 经验补充）
ForEach item 内 **@Local 在 item 创建同帧内的变化不可靠**（无论驱动 visibility 还是分支）——item 创建瞬间的初始求值就是最终布局依据；需要状态驱动的显隐必须用「item 创建前已赋最终值的 @Trace 字段」（isStreaming 模式）或回归无条件渲染。
