## 二、根因分析：空值保护缺失，TypeError 掩盖了真实状态码

### 错误解读

`Cannot read property byteLength of undefined` 是**客户端代码的运行时错误**，不是服务器的报错：

1. HTTP 响应实际已到达（否则不会进响应处理分支）
2. 服务端返回了**错误响应且不带响应体**（如 404 空 body——0.134 真机实测该端点正是「404 无 body，180ms」）
3. 鸿蒙 http 模块此时 `resp.result` 为 undefined
4. 0.136 的代码假设响应一定有内容：`buffer.from(undefined)` 抛异常 → catch 里读 `data.byteLength` 再抛 → TypeError 一路冒泡到最外层 catch
5. 结果：真实想看的信息（HTTP 状态码到底是多少）被这个 TypeError 挡住了

### 诚实记录

0.134 版本的 synthesizeTTS 有空值保护（当时真机正确显示「HTTP 404」）；0.135 播客改造覆盖了原代码，0.136 恢复时是凭 0.134 md 的描述重写的（原文已被覆盖），漏掉了这层保护。本修复把它补回来。

### 附带说明：「阶段: request」的误导

代码里「request」标记本应表示「请求没发出去」，但 then 回调内抛出的异常也会落入同一个 catch，所以响应处理错误被误标为 request。修复后该路径不再触发，无需单独处理。

## 三、修复方案（1 个文件，2 处小改）

### ApiClient.ets — synthesizeTTS 响应处理

① **空值保护**（核心修复）：

```typescript
const code = resp.responseCode;
// ★ 0.137：错误响应可能无 body（如 404 空 body），resp.result 为 undefined，
// 不做保护会在 buffer.from(data) 抛 TypeError 掩盖真实状态码（0.136 真机实锤）
const data = resp.result ? (resp.result as ArrayBuffer) : new ArrayBuffer(0);
```

② **空响应体的错误消息优化**：

```typescript
// 原：HTTP 404: （冒号后空白，看不出有没有 body）
// 改：body 为空时明确显示「响应体为空」
const errMsg = bodyText.length > 0
  ? `HTTP ${code}: ${bodyText.substring(0, 150)}`
  : `HTTP ${code}（响应体为空）`;
```

200 分支无需改动：data 为空 ArrayBuffer 时走现有「HTTP 200 但响应体为空」分支，行为正确。
