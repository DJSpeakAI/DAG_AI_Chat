## 二、第二轮根因定论（证据链闭合）

### 证据 1：真机日志——404 无响应体

方舟对**不存在的路径**返回 404 + 空 body（ApiClient 的 body 解析走了 catch 分支，日志只剩 `HTTP 404`）。若是「模型无权限/不存在」，方舟惯例返回 4xx + JSON 错误体（含 code/message）。空 body 404 指向**路径本身不存在**。

### 证据 2：webfetch 探测的 401 是误判（纠正 0.134 附录第 4 条）

不带 Key GET 该端点返回 401——0.134 据此推断「端点存在」。**这个推断错了**：方舟网关对任何路径都先统一鉴权，401 不代表路径存在。带 Key 的真机请求穿透鉴权层后返回 404，才是路径真实状态的答案。

### 证据 3：互联网零实证

- 精确搜索 `"doubao-tts-241215"`：**无任何真实匹配**——该 ID 是 0.134 方案的猜测，不存在。
- 精确搜索 `"ark.cn-beijing.volces.com/api/v3/audio/speech"`：约 50 条结果**全是无关页面**，无一篇官方文档、无一个真实调用用例。
- 反例澄清：Sourcegraph 里 clipforge/Mora 的配置、labring/aiproxy 的 AudioSpeech 适配——aiproxy 是**第三方网关**（它自己实现了 /audio/speech 适配层），不能证明方舟原生有此端点。

### 根因定论

**方舟根本没有 `/api/v3/audio/speech` 这个 HTTP 端点。** 0.133/0.134 两轮都在调用一个不存在的接口，无论换什么模型 ID、什么 voice 都必然 404。

豆包语音系（播客、语音合成、语音合成-2.0）全部走 **openspeech 系接口**（`openspeech.bytedance.com`），其中：
- **Doubao-语音播客**：`wss://openspeech.bytedance.com/api/v3/sami/podcasttts`（用户提供的官方文档确认，协议细节 0.134 已存档）
- **Doubao-语音合成-2.0**：走 TTS V3 系接口（**本项目暂无其完整协议文档**，见第五节）

好消息：播客 API 鉴权用的就是**方舟 API Key**（X-Api-Key 头），用户现有 Key 直接可用，且用户控制台已勾选授权「Doubao-语音播客」。

## 三、修复方案：改接官方播客 WebSocket API（单人朗读）

**思路**：点喇叭 = 把 AI 回复以播客音色朗读出来，正是「语音播客」模型的单人模式场景（action=3 nlp_texts）。利用 `return_audio_url=true` 拿整段音频 URL 直接播放，**绕过二进制流式音频拼接**，工程量可控。

### ① ChatModel.ets（ApiConfig）

- `audioModel` 默认值改为 `'doubao-tts-anchor-65-241005'`（Doubao-语音播客；播客 API 由 X-Api-Resource-Id 指定服务，此字段仅作界面展示与标识）
- `audioVoice` 字段**删除**（用户明确：不需要音色配置，用默认发音人）
- `audioEndpoint` 默认值改为 `wss://openspeech.bytedance.com/api/v3/sami/podcasttts`
- 新增 `@Trace audioSpeedRatio: string = '1.0'`（语速，播客 API 通用参数，默认 1.0 不动）——**待审批确认是否需要**；不需要则不加，保持最小改动

### ② ApiClient.ets：新增 `synthesizePodcastTTS()`（替换 synthesizeTTS 的调用点）

- **连接**：`@ohos.net.webSocket`（支持 ArrayBuffer 二进制帧，0.134 已查证）
- **鉴权头**：`X-Api-Key: {方舟Key}` + `X-Api-Resource-Id: volc.service_type.10050` + `X-Api-Request-Id: {uuid}`
- **请求帧**（大端序 4 字节 header + JSON payload）：
  - byte0 = 0x11（协议版本 1 + header 大小 1）
  - byte1 = 0x10（消息类型 full-client-request=0b0001 + flags=0）
  - byte2 = 0x10（序列化 JSON=0b0001 + 压缩无=0b0000）
  - byte3 = 0x00（保留）
  - payload = UTF-8 JSON：`{ action: 3, nlp_texts: [{content: "分段文本", speaker: 默认发音人}], input_info: { return_audio_url: true } }`
  - 字节值实施时**逐字节对照用户提供的官方文档截图核对**，日志打印发送帧 hex 便于校验
- **分段**：播客 API 单轮 ≤300 字符（总 ≤10000）。现有 ChatPage 已有分段逻辑，段长上限从当前值调为 280（留余量），一次 WebSocket 会话内逐轮发送
- **收帧解析**：解析 header（消息类型/序列化/压缩）+ 事件号；事件 363（PodcastEnd）的 payload JSON 里取 `meta_info.audio_url`；错误事件（如 1000 系）打完整 payload 日志
- **结束**：发 finishConnection 帧（byte1 flags=0b100）后 close
- **日志**（用户要求后台可看请求/响应）：连接成功/失败、发送帧 hex、每帧事件号、audio_url、错误码全打 `[ApiClient]` 标签

### ③ ChatPage.ets：播放链路简化

- 拿到 `audio_url` 后：AVPlayer 直接播 https URL（网络音频），**替换**现有 base64→临时文件→fd:// 链路（播客 URL 仅 1 小时有效，即时播放无影响）
- 分段播放衔接逻辑保留（若一次会话返回单一整段 URL 则单段播放，逻辑自动兼容）
- 错误 toast 保留 150 字符截断

### ④ SettingsPage.ets

- `AUDIO_MODEL_LIST` 只留一项：`{ id: 'doubao-tts-anchor-65-241005', name: 'Doubao-语音播客' }`（用户 Key 已授权；「语音合成-2.0」等 TTS V3 系模型无完整协议文档，本版不接，避免再犯无实证配置的错误）
- **删除「音色 ID」输入框**（用户明确不要）
- 音频 Endpoint 输入框保留（默认值已是播客端点，高级用户可改）
- **新增「未保存提醒」**：点返回时若编辑值与已保存值不一致，弹确认框「修改未保存，确定退出？」——堵住本次用户踩的坑（改了下拉没点保存）
- 旧值迁移：`aboutToAppear` 时若 `audioModel` 为 `doubao-tts` / `doubao-tts-241215`（0.134 的两个无效 ID）→ 重置为 `'doubao-tts-anchor-65-241005'`；`audioVoice` 字段删除后旧持久化数据自动忽略

### ⑤ 保留 0.134 已验证的部分

- 设置页触发器显示模型名字（问题 2 已修复且生效，不动）
- toast 150 字符截断（不动）

## 五、风险与兜底

| 风险 | 说明 | 兜底 |
|------|------|------|
| 二进制帧字节值与文档有出入 | 存档摘要可能漏细节 | 实施时逐字节对照用户官方文档截图；日志打印帧 hex，真机一次即可定位 |
| speaker 默认发音人不确定 | 文档有默认值，截图细节需核对 | 实施时从用户截图取默认值；错误响应会明确提示，日志可见 |
| 单轮 300 字限制 | 长消息需多轮 | 现有分段逻辑调段长上限 280，逻辑复用 |
| return_audio_url 多轮行为 | 整段一个 URL 还是每轮一个，待实测 | 播放逻辑两种都兼容（单 URL 单段播，多 URL 逐段播） |
| 「语音合成-2.0」本版不接 | 无完整协议文档，不重复无实证错误 | 0.136 候选：用户提供 TTS V3 文档截图后接入 |
| 鸿蒙 webSocket 二进制兼容 | @ohos.net.webSocket 支持 ArrayBuffer（已查证） | 若真机异常，日志帧 hex 直接暴露问题 |
