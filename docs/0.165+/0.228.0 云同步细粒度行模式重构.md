# 0.228.0 云同步细粒度行模式重构

> 2026-10-12 立项。用户需求：三端云同步接近零 bug——修复气泡树连线/布局奇形怪状、根治删卡复活、复习进度绝不分裂/不重复；设置分两类（设备级不同步/账号级同步）。用户拍板：不计工程量、要成熟方案（业界记录级同步形态）、AI 开发周期按小时计。
> 决策对话记录：本迭代前讨论轮（快照行三轮补丁史 → B 方案拍板）。

## 一、立项背景（三个 bug 的根因链，代码实锤）

1. **气泡树奇形怪状（连线/布局乱）**：三重叠加——
   - a. PC 在 0.223.x~0.224.4 窗口期一直跑旧版（1000225），旧下行逻辑「autoLayout 重排→saveTree→再上行」乒乓污染云端坐标；
   - b. `unionMergeFlatPool`（ChatModel.ets:1333）纯并集无墓碑——A 端删除的气泡在 B 端复活并回传，僵尸节点堆积；
   - c. union 只增不减，云端存量污染无自愈机制。
2. **词/卡删而复活**：CloudSyncArbiter 挂旧 key（0.218.0 建立），0.223.x 尾追字段（墓碑/水位/闸门）在升级设备上**不持久化**（0.224.1 已预言的 latent bug）；且删除墓碑传播从未真机实测。
3. **设置完全没同步**：上行只有四池（flat/tabs/word/knowledge），无任何设置行。

**架构层结论**：传输层（华为 RDB+cloudSync）零 bug；全部 bug 出在自研合并层（池快照+union+墓碑+水位+闸门）。三轮补丁（0.165 整池→0.218 union→0.223 墓碑）每轮引入新洞——手写简易 CRDT 是错误抽象，本次换引擎。

## 三、方案设计（B：一行一条，框架级仲裁）

### 3.1 行键设计（cloud_data 表结构零改动，AGC 侧零改动）

| 行键前缀 | 内容 | value |
|---|---|---|
| `node:<id>` | 一个 BubbleNode（含 messages） | 节点 plain JSON（手写映射，0.205.4 纪律） |
| `tab:<id>` | TabMeta（选项卡+树） | tab plain JSON |
| `word:<id>` / `card:<id>` | 词条/卡片（含记忆进度、标签、图片） | 复用 BackupUtil wordToPlain/cardToPlain |
| `wfolder:<id>` / `kfolder:<id>` | 两库文件夹 | folderToPlain |
| `cfg:<name>` | 账号级设置（api-config / ai-pref / face-mode） | 设置 store 序列化 |

- `updated_at` 列 = 条目业务 mtime（下行 reconcile 语义裁决用）；框架 TIME_FIRST 用自己的行时间戳做搬运裁决，两者分工：**框架管搬运，条目 mtime 管语义**。
- 主键唯一（端云硬约束）→ **重复卡片结构上不可能**。

### 3.2 上行（替代四池快照）

- 条目咽喉：增/改 → `upsertRow`（**diff-cache**：内存 Map<key, lastValue>，值变才写行——杀行时间戳 churn；**生命周期：重启后由首轮全表 reconcile 从本地 RDB 重建**（P0-3 吸收）；序列化 canonical=手写 plain 映射字段顺序恒定）；删 → `deleteRow`（框架传播删除，**墓碑机制整套删除**）。
- 挂点：noteBankMutation 现有挂位改条目级（保留 3 秒防抖，**node 行坐标变更共用同款防抖窗口**——豆包高频防抖吸收）；saveTree 挂位 → node/tab 行；三个账号级设置的保存点 → cfg 行。
- **闸门期变更不丢（P0-5 吸收）**：rowInitDone 打开后执行一次**全量 flush**（本地全条目 vs diff-cache/cloud 行比对，仅差值写行）——被闸变更零丢失补写；闸门失败保持关闭（0.223.x 语义），下次前台重试，离线期间本地数据永远安全。
- **首拉闸门保留**（arbiter v2 `rowInitDone`）：首轮「拉全表+reconcile」完成前禁一切行写入——0.223.1「种子顶掉云端真实数据」事故的时序防线，行模式下同样存在（TIME_FIRST 比 wall-clock，本地今天写的种子行会胜云端三天前的进度行）。
- **种子路径不戳 mtime**（结构性防线）：预置数据 mtime=0 → reconcile 时云端进度行（mtime>0）必胜 → 0.223.1 事故双保险。

### 3.3 下行（dataChange → cloudSync → 全表 reconcile）

- 保留已验证模式：SUBSCRIBE_TYPE_CLOUD 订阅 + forceCloudSyncNow 完成后**全表 query**（行数几百级，本地 RDB 查询毫秒级）→ **per-item reconcile**：同 id 条目 mtime 大者胜 → 写回 PersistenceV2。
- **★ 已知行键集合（删除检测，双 AI 评审 P0-1 吸收）**：全表 query 只能看到「还存在的行」，看不见「云端已删除的行」——维护本地持久化已知键集合（arbiter v2 内 JSON），reconcile 时「已知集合有、当前全表无」的键 → 判定远端删除 → 删本地对应条目。自删场景幂等（本地条目已删，再删一次无副作用）。
  - **全空守卫**：已知集合非空且云端全表为空（用户在云空间手动清空数据）→ 不自动清本地，保留本地数据等下一轮上行重建，防误操作灾难（豆包·云端反向删除吸收）。
- **一致性说明**：全表 query = 同步完成后单点快照，天然规避 node/tab 半更新态（这也是选全表而非逐行事件的原因）；缺失节点的 tab 容错解析（deserialize 已有容错）。
- 回声挡：序列化值相等跳过（canonical 手写映射字段顺序稳定）。
- 气泡写回走 `needsCloudRedraw`（0.223.0 保坐标重绘机制**原样保留**，BBTreeCanvas 零改动）。
- SUBSCRIBE_TYPE_CLOUD_DETAILS 按行精准通知（含删除位置）= 后续优化项（ChangeInfo 结构实施首日读 d.ts 核对，不阻塞本期）。

### 3.4 删除

- 本地删条目 → 删行 → 框架传播。**unionMergeFlatPool / mergeRecords / unionTomb / 墓碑管理 / 池级水位（mtimeFlat 等）全部删除**（约几百行最容易出 bug 的自研代码清零）。
- **★ delete-wins 风险（双 AI 评审 P0-2 吸收）**：TIME_FIRST=修改时间近者胜，**不保证删除优先**——B 断网删卡、A 同时编辑、B 回网后 A 的更新可能重建行→复活。处理：探针 B 实测终态；若框架确实是 update-wins → 启用轻量删除标记（`del:<id>` 行或行内 deleted 字段，二选一按探针结果定），**不预先实现**、按证据决定。
- 唯一边界（用户已知情）：同一张卡在同步窗口内被两台设备都评分 → 较早评分被覆盖（丢一次评分，不重复不分裂不排期错乱）——CloudKit/Firestore 同款默认语义，单人顺序使用几乎触发不了。

### 3.5 迁移（一次性，marker 持久化，分阶段可熔断）

1. **本地备份**：迁移前旧四池数据经 BackupUtil 内备份管线落 filesDir（0.205.0 双备份机制复用）；
2. **写行**：读四池行 → 爆成条目行（条目 mtime 沿用池内已有字段；**无 mtime 的旧真实数据=池行 updated_at 兜底，绝不用 0**——种子恒 0、旧数据恒 >0，两类天然区分（双 AI 评审 P0-4 吸收））；
3. **条目数守恒校验**：旧池条目总数 == 新行条目总数，误差超阈 → **终止迁移（池行未删=数据仍在，下次启动幂等重试）**（豆包回滚熔断吸收）；
4. **删四池行**：校验通过才删（删除传播=云端旧结构连带清除）；
5. **清污**：迁移后用户在任一端手动删除僵尸气泡（这次删除会真正传播）+ 一次「适应全图」（autoLayout）→ 全端收敛干净布局。
6. 未上架单用户：三台同次升级窗口装完即可，无兼容层。上架发版检查项：新用户全新安装无迁移负担；旧版本用户开云同步提示「请升级到最新版本」；升级弹窗提示「建议先导出本地备份」。

## 四、实施顺序（探针先行）

**第 0 步·探针实测（✅ 2026-10-12 已完成，Pad+PC 双端，CLI 编排 aa start --ps + hilog DAGAI_PROBE）**：
- ✅ 写入/更新传播可靠；**TIME_FIRST 行级 LWW 实证**（PC 写 v1→Pad 30s 后写 v2→PC 拉到 v2 双端收敛）
- ❌ **物理删行不传播**（两轮健康 sync 下复测：Pad 删+sync code=0，PC 拉取后原值原样回来；云端保留行）→ **删除设计定稿=del 标记行**（`del:<id>` 独立云行存删除时刻，写入通道传播可靠；实体行本地删除仅做本地清理；reconcile 见 del 行→删本地条目；条目 mtime>del 时间→编辑胜复活；FIFO 500）
- ❌ **行体积 1MB 过 / 3MB 败**，且**超限行毒化整批 sync**（code=1，全端数据管线卡死，删毒行后恢复 code=0）→ **分块必须做**：桥接层通用 value 分块（≥512KB 拆 `<key>~<n>` chunk 行，读侧重组，对领域逻辑透明；含图卡片/多图消息节点全覆盖）——不做分块=一张多图卡弄死整端同步
- ✅ 批量 500 行×1KB 秒级同步（5000 档未测——个人数据量几百条+分块保小行，风险可忽略）
- ⚠️ cloudSync promise 单位毫秒即 resolve、Y1 进度回调延后 ~120ms——「完成」判定不能只等 promise，reconcile 触发=dataChange 事件+回前台+固定延迟，容忍最终一致（现有池模式同款语义）
- 探针残留：~506 行 probe: 前缀垃圾行留在云端（行模式代码按前缀忽略，无害；AGC 控制台可清非必需）

第 1 步起按第三节实施（探针实证修订版）→ 三台装机 bm dump 实锤 → 验收。

## 六、风险点

1. 探针 B 终态未知 → 探针先行、reconcile 对齐实测（若框架删除与更新冲突行为怪异，回退方案=A 修补版带实测证据回来）；
2. 行体积上限未知 → 探针 C + ASSET 兜底；
3. TIME_FIRST 框架时间戳与业务 mtime 极端不一致（时钟偏差）→ 语义裁决一律以条目 mtime 为最终真相源；
4. @ObservedV2 plain 手写映射纪律（0.205.4）——node 行必须手写，禁 JSON.stringify 直序列化；
5. 迁移窗口期旧版设备池写入会被新版吸收后删除——三台当日齐升即可（未上架）；
6. StatisticsStore/attention 等「只增不减」聚合数据本期不同步（设备级），未来如需跨端汇总再立项；
7. autoLayout 上行边界：**用户显式重排（适应全图）= 照常上行（清污依赖）；下行路径绝不 autoLayout 重排再上行（0.223.0 铁律）**——实施时核查 applyCloudRedraw 空树回落分支的 saveTree 调用链；
8. 诊断日志与脱敏：探针/迁移诊断日志**须先入档再保留**（0.222.15 判定线：MEMORY 有档=特性、无档=调测残留）；diff-cache/冲突日志禁打印 value 与 API Key。

## 七、验收标准

1. 三台任意一台：改气泡（含手动拖布局）/删气泡 → 其他端 10s 内（前台）一致，**坐标与源端一致、连线正确、删除的气泡不再复活**；
2. 词/卡：新增（含图片/标签/文件夹）/编辑/评分进度/删除（含文件夹级联）三端一致；**同一词条两端先后评分 → 收敛单一排期，无重复条目**；
3. 设置：API 配置/AI 偏好/卡面模式改一端 → 其他端生效；每日复习量改一端 → 其他端**不变**；
4. 全新安装（清数据）登录开同步 → 全部数据恢复（含图片/文件夹/进度）；
5. 旧版升级（不清数据）→ 数据零丢失（迁移吸收池行）；
6. 全新安装种子数据不顶云端进度（mtime=0 防线 + 闸门）；
7. 三台 bm dump 实锤 versionCode 1000244。
8. **压力/边沿场景（双 AI 评审补充）**：迁移中杀进程重启→幂等续跑不重复；三端同时改同一气泡坐标/同时删文件夹/同时评分→收敛一致；长时间离线大量变更回网→追平无丢失；退出账号换账号登录→数据按华为账号天然隔离（云空间隔离）验证；账号级设置冲突→最后写胜（LWW 语义写明）。
