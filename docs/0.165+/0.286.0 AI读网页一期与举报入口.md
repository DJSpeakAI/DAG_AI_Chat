# 0.286.0 AI 读网页一期（纯客户端抓取）+ AI 消息举报入口

## 一、需求与决策（用户拍板）

- 用户经常需要"发链接给 AI，AI 读网页"。所配模型为腾讯云官方 DeepSeek（纯语言模型，无联网能力）。
- 架构三选（纯客户端抓取 / 阿里云服务端中转 / 第三方正文 API），用户拍板 **A：纯客户端抓取**——零服务端、合规增量最小；抓取失败不硬撑，给友好提示，二期按真实失败率再定兜底。
- 用户补充：模型走腾讯云官方通道（算法备案责任在服务方）；ICP 备案已提交，APP 备案等 ICP 下来再办；直接开工。
- 合规背景：华为应用市场 AI 类审核要求——AI 模块需举报入口（材料 G.3.8）、AIGC 显式标识（已有 0.247.3/0.278.4「内容由 AI 生成 · 仅供参考」全局行）、隐私政策须披露网址处理方式。

## 二、技术方案

### 1. 新增 utils/WebFetchUtil.ets（纯函数 + 抓取链）

- `detectWebUrls(text)`：正则提取 http/https URL，去重，上限 **2 个**（防 token 爆炸多扣 SP）。
- `extractReadableText(html)`：**纯函数**（ohosTest 断言）——剥 script/style/nav/header/footer/aside 等块 → 块级标签转换行 → 去标签 → 解码常见 HTML 实体 → 压缩空白 → 截断 **6000 字符**（尾部标注已截断）。
- `fetchWebPageText(url)`：http GET（UA 浏览器伪装，connectTimeout 8s / readTimeout 12s，2xx + text/html|plain 才收；错误全部中文化）。
- `fetchWebContextForMessage(text)`：全链入口——检测 URL → 逐个抓取 → **网页正文过 ContentFilter.checkInput（命中即丢弃该网页块并标注跳过——网页内容不拦截发送，只跳过注入）** → 拼 system 注入块（成功正文 + 失败原因均列出，模型不瞎编）。

### 2. ChatPage 集成（复刻 0.235.0 划词引用注入模式）

- 注入点：`sendMessage` 内 `buildBranchMessageList` 之后、长度 prompt 之前——**网页块只拼进本次请求的上下文副本（system 消息），气泡原文/持久化/Schema/后续轮次零改动，一次性消费**。
- 等待态：streamPhase 新增 **4=正在读取网页**（waitingView 五元分支，复用 0.191.0 体系；抓完恢复 1）。
- 结果提示：成功 toast「已读取 N 个网页」；失败 toast「网页读取失败，已按原文发送」——失败不阻断发送。

### 3. AI 消息举报入口（材料 G.3.8 模块级要求）

- AI 操作行刷新钮后加 flag.svg 举报钮 → ChatPage 自绘确认弹窗（复刻 deleteConfirm 模式，暗紫语言，禁系统灰弹窗）→ 确认拉起 `mailto:` 邮件（复刻 0.253.0 openComplaintMail 链路：openLink + 无邮件应用降级复制邮箱+toast）；正文自动附模型 ID + 版本。
- 用户消息操作行不加（举报对象=AI 生成内容）。

### 4. 隐私政策披露（材料第 4 条）

- `Agreement.ets` PRIVACY_SECTIONS 第 2 条尾部追加：消息含网址时，应用从设备直接访问该网页提取文字内容、连同消息发往用户配置的 AI 服务商；网址与网页内容不上传开发者服务器。
- `AGREEMENT_VERSION 2→3`（数据处理方式新增，按 0.264 先例重新征求同意——存量用户首启门禁重弹一次，合规正解）；版本行 v2.1、生效日期 2026-10-21。

## 四、风险点

- JS 重渲染页/反爬站抓不到 → 一期接受，toast 明示，不硬撑（用户拍板）。
- 网页正文超长多扣 SP → 6000 字符截断 + 最多 2 个 URL 双闸。
- 网页内容夹带敏感词 → 过 ContentFilter，命中丢弃该网页块（不拦用户消息本身）。
- 协议 v3 重弹门禁 → 合规必需；如用户不接受可回退版本号（正文保留）。

## 五、验收标准

1. 消息含 URL：等待态出现「正在读取网页」→ AI 回答基于网页内容；气泡原文仍是用户原文字。
2. 无 URL 消息：链路零变化（不抓取、无 toast、无注入）。
3. 网页失败（断网/反爬）：不阻断发送，toast 提示，AI 按原文回答且知道该网页读取失败。
4. AI 操作行出现举报钮 → 确认弹窗（暗紫）→ 拉起邮件/降级复制邮箱。
5. 隐私政策第 2 条含网址披露句；首启门禁对存量用户重弹。
6. ohosTest WebFetch 断言全绿；主模块+ohosTest BUILD SUCCESSFUL。

# 追记：0.286.2 壳页走隐形 Web 组件渲染重取（2026-10-21 当日二审）

用户实测 0.286.0：文档站（前端渲染 SPA）只抓到「文档中心」四字+标题壳。用户点破技术路线：静态 HTTP 拿不到，须 Web 组件注入脚本取 innerText。

## 方案（两级瀑布，纯客户端不变）

1. **静态抓快通道**（1~2s）：正文 ≥300 字直接用（普通网页不受影响）。
2. **壳判定**（<300 字）或静态失败 → **ChatPage 按需挂载 1×1 隐形 Web 组件**（@kit.ArkWeb 项目首用；javaScript+domStorage 全开）真渲染 → onPageEnd 后轮询注入脚本取 `document.title + document.body.innerText`（首轮 800ms、不足 300 字再等 1000ms×最多 5 轮——SPA 异步出文）→ 15s 整页超时兜底（有字给字）。
3. 渲染后仍短 → 静态短正文兜底并标注「内容不完整」；全失败 → 失败原因进注入块（模型不瞎编）。
4. 串行队列（一次渲染一页，≤2 页），队列空即卸载组件；aboutToDisappear cleanupWebRender 清定时器+挂起 Promise。

## 关键技术点（踩坑入档）

- runJavaScript 返回的字符串是 **JSON 编码的**——必须 JSON.parse 解包。
- Web 组件 controller 在 **onControllerAttached 前调用必抛异常**——ready 门卫时序。
- **onPageEnd ≠ SPA 渲染完成**——轮询 innerText 长度是出文可靠判据。
- iframe 内文档取不到（runJavaScript 仅主 frame）= 已知边界。
- INTERNET 权限已有，Web 组件零新增权限。
