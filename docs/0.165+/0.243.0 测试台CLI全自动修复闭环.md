# 0.243.0 测试台 CLI 全自动修复闭环（方案文档·待用户裁决开工）

> 状态：**方案讨论稿**（2026-10-16）。用户已拍板方向：直接上全自动修复（不做半自动链）；协作交接维持「桌面 md + 人工 Ctrl+C/V」现状不变。
> 本文档按用户要求产出：需求 / 可行性 / 预期结果 / 改动文件清单 / AGENTS.md 必要性与全文。

---

## 一、需求背景（用户原话提炼）

1. 现状痛点：测试台报错后只生成文档放桌面，用户手动复制给某个 AI 修，修完再手动跑测试——链路断了，人工当传送带。
2. 目标：**测试台发现失败用例 → 自动派单给 DevEco Code CLI → CLI 自动改码 → 编译装机 → 重跑测试 → 全绿收工 / 死胡同熔断**，全程零人工（唯一人工=点一次启动 + 华为授权弹窗类系统红线）。
3. 前置共识（2026-10-16 用户拍板）：
   - 双 AI 协作交接**维持现状**：md 放桌面、用户 Ctrl+C/V 发给任意 AI。拒绝「交接目录+接单口令」方案（本质仍是人工中转，换汤不换药，且口令可能引起 AI 歧解）。
   - 用户效率优先于 token：CLI 干活期间用户与 CodeArts 并行讨论下一单，流水线吞吐优先。
   - 每个任务首句固定贴：「先读 project_rule.md、MEMORY.md、docs/CONTEXT_MANAGEMENT.md，对齐基线后再开始任务。」
4. 工程背景：CLI 曾在难 bug 上多轮空转甚至爆 32G 内存——闭环必须内置**止损熔断**，且优先采用**一次性进程**形态（headless）杜绝常驻膨胀。

## 二、目标与预期结果

- **结果态**：用户在测试台点一次「自动修复」→ 系统自动循环「测试→修复→编译→装机→重测」→ 三种出口：
  1. **绿**：产出修复报告（改了什么/几轮/git 打点记录），工作区留给用户验收；
  2. **死胡同**：连续 N 轮不收敛 → 自动生成「死胡同报告.md」放桌面（五部分求援定式）→ 用户拿去发任意 AI（豆包/DeepSeek/CodeArts）→ 方案回来喂 CLI 继续；
  3. **红线拦截**：改动触碰数据安全红线文件 → 立即回滚+熔断转人工。
- 附带收益：headless 一次性进程天然解决「CLI 常驻爆内存」问题（每轮任务新进程、干完即退）。

## 三、可行性分析

### 3.1 关键前提（唯一硬依赖）：DevEco Code CLI 的 headless 能力

即：CLI 支持**非交互一次性执行**（命令行直接下任务、干完自动退出、输出可解析），类似 `claude -p` / `codex exec` 模式。

**验证步骤（Phase 0，10 分钟内可完成）：**
```sh
# ① 确认命令名与帮助（在 DevEco Terminal 或系统 shell 里）
<cli命令> --help
# 找这些关键词：-p / --prompt / exec / --non-interactive / --print / -q（quiet/一次执行）
# ② 试跑最小任务（验证非交互执行+自动退出+退出码）
<cli命令> -p "读 README.md 第一行并原样输出" 
# 判定：不进交互界面、自动退出、$? 有退出码、stdout 有内容 → headless 成立
# ③ 试跑项目内小任务（验证它能读仓库+改文件）
<cli命令> -p "在 entry/src/main/ets/utils/ 下新建 _autofix_probe.txt 内容 ok，完成后删除"
```

- **若支持** → 走本方案全自动闭环（Phase 1~4）。
- **若不支持** → 降级路径 B：测试台把「修复任务包」自动生成 md 放桌面 + 页面一键复制按钮，用户贴进 CLI 交互窗口（半自动，人工只剩粘贴）；后续再探 CLI 是否有管道/SDK 模式升级。
- CLI 命令名/参数以华为官方文档或 `--help` 实测为准，本文档不猜测具体写法，落码前必须实锤。

## 四、总体架构

### 4.1 闭环链路

```
[用户点「自动修复」]
   ↓
健康检查（三灯：CLI 存在性 / 模型连通 / 编译链+设备在线）——任一红=拒绝启动并亮原因
   ↓
跑指定测试套件 ──全绿──→ 出修复报告，收工
   ↓ 失败
生成「修复任务包」（失败用例+断言详情+证据+红线禁碰清单+止损令+基线三读指令）
   ↓
git 自动打点（autofix-round-N，可回滚）
   ↓
headless 调 CLI 改码（独立进程，超时 600s 强杀）
   ↓
红线 diff 检查（git diff --name-only vs 红线清单；命中=回滚+熔断转人工）
   ↓
编译 → 装机 → 重跑测试
   ↓
收敛？──是→ 回到「跑测试」确认全绿 → 出报告收工
   └─否→ 轮次+1；连续 ≥ maxRounds(默认2) 不收敛 → 熔断：
          生成「死胡同报告.md」→ desktopDir 桌面 → 前端亮红提示
          （用户人工外发求援；拿回方案后可重新点「自动修复」继续，从打点续跑）
```

### 4.2 止损熔断判据（写死在服务端，不靠 CLI 自觉）

| # | 判据 | 动作 |
|---|---|---|
| 1 | 同一 bug 连续 maxRounds(默认 2) 轮修复后测试仍失败 | 熔断→死胡同报告 |
| 2 | 本轮 git diff 为空（CLI 没改成任何东西） | 直接判死轮，计入熔断 |
| 3 | diff 触碰红线文件清单 | 回滚本轮+熔断转人工 |
| 4 | headless 进程超时 600s | 强杀+判死轮 |
| 5 | 编译失败连续 2 轮（CLI 改崩了） | 熔断（把编译报错写进死胡同报告） |

### 4.3 红线文件清单（config.json `autofix.redlineFiles`，初版）

- `entry/src/main/ets/model/*`（Schema 铁律：字段只许尾部追加，自动改禁碰）
- `entry/src/main/ets/utils/CloudSyncUtil.ets`（云同步仲裁）
- `entry/src/main/ets/utils/BackupUtil.ets`（备份恢复）
- 任何 PersistenceV2/AppStorageV2 的 key 字符串（禁改 key）
- `AppScope/`、`signing/`、`entry/src/main/module.json5`（签名/包名/云服务配置）
- `testing/console/` 本身（防闭环改测试来"骗绿"——**测试代码对自动修复不可见不可改**）

> §4.3 第 6 条尤其重要：自动修复只许改**业务代码**，不许改测试断言本身，否则闭环会「把考卷改对」。

### 4.4 死胡同报告模板（沿用已验证的五部分求援定式）

①环境与现象（版本/设备/失败用例）②相关代码骨架（CLI 已定位的文件与函数）③已实锤的平台事实（hilog/artifacts 证据）④已试方案+死因表格（每轮 diff 摘要+测试结果）⑤怀疑方向与求解点——生成后放桌面，用户外发。

## 六、AGENTS.md（新建，全文如下）

**必要性**：用户习惯是每个任务首句贴「先读三文档」。AGENTS.md 是业界通用约定（多数 CLI agent 自动读取仓库根的 AGENTS.md）——写一份放仓库根，①支持的工具自动获得规则（连「先读三文档」那句都可省）②不支持的照旧手动贴。一次维护，任意 AI 通用。git 随仓库同步老机器，无需用户手动转存。

```markdown
# AGENTS.md — DAG AI Chat 项目 AI 协作规则（所有 AI 工具通用）

## 强制第一步
任何任务开始前，先读三文档对齐基线：
1. project_rule.md（全局开发规则）
2. MEMORY.md（项目基线+迭代记录，只读最新条目定位上下文）
3. docs/CONTEXT_MANAGEMENT.md（上下文纪律）

## 开发铁律（摘要，细节以 project_rule.md 为准）
- 技术栈：鸿蒙 ArkUI V2 + @ObservedV2/@Trace；禁止混用 V1 老语法
- 数据 Schema 字段只许尾部追加+默认值，禁止改名/改类型/删除（数据安全第一）
- PersistenceV2/AppStorageV2 的 key 一律禁改
- 发版版本号三处同步：AppScope/app.json5 + Index.ets + GlobalSettingsDialog.ets；versionCode 每版 +1
- 收尾四件套：MEMORY.md 迭代记录 / 桌面清理 / git push 双远端 / 版本号三处同步
- 一任务一会话：任务完成即收尾，bug 修复新开会话

## 止损熔断（强制，防死循环烧资源）
同一 bug 出现以下任一情况，立即停止修改，产出「死胡同报告.md」（放桌面）：
1. 连续 3 轮修改+编译仍未解决
2. 同一处代码第 2 次改回原样
3. 修改范围超出原始 bug（≥3 文件或开始重构式改动）
4. 编译报错数连续 2 轮不降反升
死胡同报告五部分：①环境与现象 ②相关代码骨架 ③已实锤证据 ④已试方案+死因表 ⑤怀疑方向。
报告产出后必须停手，等人工决定下一步。

## 红线（禁改，改动须转人工）
数据模型 Schema / CloudSyncUtil.ets / BackupUtil.ets / 持久化 key / signing/ / module.json5 / 测试台 testing/console/

## 其他
- 未经用户明确要求不执行 git commit
- 桌面「测试台.html」是副本禁手改（正本 testing/console/）；桌面「埋点看板.html」禁删
- 全程简体中文
```

## 七、风险点与对策

| 风险 | 对策 |
|---|---|
| CLI 无 headless 模式 | Phase 0 先验证；不支持走降级 B（任务包 md+一键复制），闭环骨架保留 |
| 自动改码碰坏数据 | 红线 diff 检查+每轮 git 打点可回滚+红线文件根本不给改 |
| 闭环「改考卷骗绿」 | 测试代码（testing/console、ohosTest）对修复任务不可见不可改 |
| 进程卡死/内存膨胀 | headless 独立进程+600s 强杀；杜绝交互式常驻会话 |
| 设备离线/锁屏 | 健康检查含设备在线探测；离线拒绝启动 |
| 模型欠费/限流 | 健康检查试跑探针；失败亮红指因 |
| 编译装机耗时拉长循环 | 每轮限时；ARKUI-TEST 类长用例可排除在自动闭环套件外（config 可配） |

## 八、验收标准

1. **健康检查**：CLI 未安装/模型欠费/设备离线三种场景，均红灯拒绝启动且原因中文明示。
2. **简单 bug 自动修复**：人为改坏一处 UI 实现（如颜色写错致 UI-AUDIT 用例红）→ 点「自动修复」→ 闭环自动修复→编译→装机→重测转绿→产出修复报告，git 历史可见 `autofix-round-N` 打点。
3. **死胡同熔断**：人为制造难 bug（2 轮修不好）→ 熔断 → 桌面出现死胡同报告.md（五部分齐全）→ 仓库自动回滚到打点。
4. **红线拦截**：人为诱导改动 Schema 文件 → 当轮回滚+熔断转人工提示。
5. **全程零命令行**：除点按钮外无任何人工命令；headless 进程退出后内存平稳。
