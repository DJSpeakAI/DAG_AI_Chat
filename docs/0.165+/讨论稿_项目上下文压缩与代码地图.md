## 二、AOCI 是什么（已查实，一手资料）

**AOCI-CODE**（github.com/aoci-spec/aoci-code，1.6k★，Go 单二进制，v0.1.0-rc21，FSL-1.1-MIT 许可，GitHub Trending 常客，配套论文 arXiv 2605.02421）：

> **AOCI（AI-Oriented Cognition Infrastructure）= 位于 AI Agent 与软件系统之间的认知基础设施**——把代码/配置/测试/数据库结构压缩成**符号+语义结合的高密度纯文本索引**，Agent 开工前读一次索引就认识整个系统，而不是每个任务重新搜索、重读整个代码库。

### 核心机制：FRAS 语义条目（这是它比我上轮猜的 Repomix/DeepWiki 都对口的原因）

模型给**每个文件**写一行四字段条目：

| 字段 | 回答的问题 | 套在我们项目上的样子 |
|---|---|---|
| **F — Function** | 这个文件负责什么 | `ChatPage.ets: F:对话页主体，气泡渲染/流式接收/划词/导入动画` |
| **R — Relations** | 改它时必须连带看什么 | `R:ChatModel.ets,ApiClient.ets,MdInline.ets` ——**治"改 A 坏 B"** |
| **A — API** | 对外暴露什么契约 | `A:buildBranchMessageList,consumePendingImport` |
| **S — 非显而易见约束** | 不能从结构推出的血泪教训 | `S:ForEach item 内 visibility 初始求值必须 Visible（0.160.x）；评分区禁入横向 Scroll（0.198.3 铁律）` |

**S 字段 = 我们 200+ 版本踩坑教训的天然归宿**——MEMORY 里的铁律大多其实是"某个文件的非显而易见约束"，现在全堆在 MEMORY 里撑大注入，AOCI 把它们**归位到具体文件头上**，AI 精读该文件时才加载。

### 四大特性（对着我们的痛点）

1. **持久化 + Git 版本化**：索引是项目里的纯文本文件（aoci.txt/aoci.code.txt/aoci.meta.txt），随代码走、可 diff、可回滚——跨会话/跨 Agent 认知不丢（治我们的"新会话重新摸象"）。
2. **自动维护**：MCP 发现代码变化 → Agent 开发完顺手补条目 → 索引与代码版本一致（类似我们收尾四件套，但机器强制）。
3. **规模指标**：实测 70 万行系统 ≈ 300K token 索引；我们 36,090 行估 **15~25K token**（压缩率 ~95%，一次建索引约 10~15 分钟）。
4. **本地优先安全**：不联网、不存凭据、不上传，索引由自己的 Agent 用自己已有的模型通道撰写——符合项目数据安全红线。

### 与上轮候选的关系（一段讲清）

- Repomix（打包全量）→ 装不下 128K 窗口，淘汰；
- DeepWiki（AI 生成 Wiki）→ 只讲架构不讲"哪个文件哪行有什么雷"，弱一层；
- Serena/Aider RepoMap（纯符号签名地图）→ 无语义无教训，弱一层；
- **AOCI = RepoMap 的符号定位 + DeepWiki 的语义蒸馏 + S 字段的教训归位 + Git 治理，四合一**。README 明说与 CodeGraph/RAG/LSP 的分工对比：索引用来**认识系统**（开工前一次读），查询工具用来**干活时取代码**——两者互补不替代。

## 三、我们能做什么：两条路线（可先 B 后 A）

### 路线 A：直接接入 AOCI-CODE（工业版，工具链一步到位）

**标准流程**（官方"一键使用"）：下载 Release 二进制 → `aoci init --locale zh-CN --agent <宿主>` → `aoci scan` → 重启 Agent → 让 AI 建索引 → `aoci verify/check` 验证对齐 → 日常开发 MCP 自动维护。

**⚠️ 本机适配风险（关键决策点，先说实话）**：
- AOCI 是 Go 单二进制，官方 Release 大概率只有 linux/darwin/windows 构建；**OpenHarmony PC 无官方 GOOS 目标**，本机直接跑 CLI/MCP 存疑（需实测：有 linux-arm64 musl 兼容的可能，但没有承诺）。
- **可行的混合路径**：索引本质是纯文本文件 + Git 版本化，**在哪台机器生成无所谓**——老机器（Windows，build-server.ps1 那台）跑 AOCI 生成索引 → 索引文件随 git 走 → 鸿蒙 PC 上 DevEco Code 的 AI **直接 Read aoci.code.txt**（核心价值全保留），只是失去 MCP 自动维护/漂移检测（维护回老机器做，或手工按 FRAS 格式补条目）。
- DevEco Code 不在官方宿主清单（Codex/Claude Code/Cursor/OpenCode/Qoder），走"其他 MCP Host：标准 stdio Server 手工配置"路径，或干脆不用 MCP 只用文本。
- rc21 仍是 RC 版本；FSL 许可个人使用无碍。

### 路线 B：自建 AOCI-lite（借鉴 FRAS 思想，零外部依赖）

- 我们已有的资产几乎能拼出 80%：collect_source.js（软著脚本，文件遍历骨架）+ collect_source 输出的行数统计 + MEMORY 铁律库 + Read 工具按行号精读能力。
- 做法：**手工/AI 按 FRAS 四字段给 63 个文件各写一条目**（一次性任务，我就能干，约 1~2 小时），生成 `docs/AOCI_INDEX.md`；格式完全照抄 AOCI（目录段 + basename[标签] + F/R/A/S），将来若接真 AOCI 可直接换壳。
- 缺什么：无治理工作流（漂移检测/验证对齐/自动维护），纯靠收尾纪律（收尾四件套 → 五件套："改了受影响文件就补 S/F 条目"）。
- 优点：今天就能落地，零环境风险，且写作过程本身就是一次全项目认知对齐。

### 两条路线不冲突：推荐 **B 先行（本周）→ A 视条件跟进（老机器实测）**

### 配套不变项（上轮方案 D 仍然独立成立，与 AOCI 互补）

- **MEMORY.md 减肥**（治注入层，AOCI 治文件层，两者正交）：0.1x~0.21x 老条目迁 docs/MEMORY_ARCHIVE.md，MEMORY 保留 FACT/PENDING/活规则+近 30 版，注入成本 260KB → 80KB。铁律类条目迁入 AOCI-lite 的 S 字段（按文件归位）或 project_rule（全局性保留）。
- 版本归档与红线核查同上轮：纯文档/工具链新增，不碰业务代码、Schema、持久化 key、testing/。

## 四、AOCI 视角下的同构彩蛋（发散种子，用户专属）

气泡树 summaryHead（距离1全文/距离2标题/≥3不注入）≈ Claude Code Section 注册表（cached/uncached）≈ AOCI Whole-Index（开工前一次读、干活时按需展开）≈ MEMORY 活规则 vs docs 归档。**同一压缩思想第五层落地：这次终于轮到"AI 开发者看我们自己项目"这一层。**而且 AOCI 的 S 字段设计（"S 不是摘要，是不可从结构推断的约束"）和我们 Prompt 军规第 3 条"失败模式接种"完全同构——它把接种做到了基础设施层。
