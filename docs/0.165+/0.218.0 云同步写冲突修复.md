## 一、事故与定性（用户实测+代码实锤）

**用户实测（100% 采信）**：
1. 三台设备系统侧云空间开关全开（云同步三层金字塔全通，端到端已打通——AGC 调测页有 flat_pool 数据行、Pad 能收到下行）
2. **PC 开云同步约 10 分钟后本地气泡数据被清零**（严重数据事故）
3. Pad 下行出现异常气泡（默认标题"空气泡 0 条对话"×3，与 PC 重建的气泡可能对不上）
4. autoSync 非实时（数据延迟十几分钟，系统择机批量推——切后台/网络空闲时），用户已理解

**根因定性（代码链实锤）**：
- **双端写冲突 + last-write-wins 无仲裁**：cloud_data 表 key='flat_pool'/'tabs_pool' 存整棵树的 JSON 快照，`upsertCloudData` 用 ON_CONFLICT_REPLACE 覆盖写（CloudSyncUtil.ets ~205 行）
- 两台设备都激活 autoSync 后各自 upsert 同一 key → **后写覆盖先写**
- 下行链路（subscribeCloudDownlink → pullAndNotify → ChatModel 侧 handler）：handler 只做「值 != 本地池」比较挡回声，**挡不住另一台的旧值**——Pad 旧/空树上云下发到 PC → PC handler 判"不相等"→ 整树写回 → **PC 数据被 Pad 旧树覆盖清零**
- 0.165 时代只调通"手机写、Pad 读"单向场景；2026-10-10 双端同写第一次发生即爆雷

## 三、修复方案（三选一或组合，需与用户讨论拍板）

- **方案 A 单写端模式**：同一华为账号只允许一台"主写端"（如最后活跃设备），其余只读下行。实现最简单，但多端切换体验差
- **方案 B updated_at 时间戳仲裁（agent 倾向，最小改动）**：下行写回前比快照 updated_at 与本地最后写入时间戳——云端值旧于本地则**丢弃不写回**（防旧树覆盖）；上行 upsert 已带 updated_at。坑：RDB 表 updated_at 由本端写，时钟偏差可容忍（分钟级）；但"两端都改过"时仍是丢一端（last-write-wins 保留，至少不回退清零）
- **方案 C 节点级合并**：快照内按 nodeID 做三路合并（本地+云端+共同祖先），冲突提示用户。体验最好工程量最大
- 无论选哪个：**写回池前先把被替换的树存一份本地备份**（如 key 'flat_pool_backup'），数据安全兜底
- 修复合须含回归场景：双端同开→A 建气泡→B 建气泡→互不覆盖/不清零

## ★ 2026-10-10 深夜用户拍板（最终定案，新会话直接按此开工）

**方案 B：updated_at 时间戳仲裁（最新者胜）**。用户理由：个人用户产品，同一用户不会双端同时改同一内容，不需要 C 的节点级三路合并（那是团队场景）；"以最新的为准，时间戳没问题，因为是同一个人"。

**粒度决策（用户放权给 agent，定案如下）**：
- **保持现有两池粒度不动**：key='flat_pool'（平铺池快照）+ key='tabs_pool'（Tab 池快照）。理由：气泡节点会在两池间移动（平铺/选项卡双模式互通），按单节点拆 key 会引入节点归属+ID 冲突复杂性，比整池快照更险
- 仲裁单位=每池独立仲裁（flat_pool 和 tabs_pool 各自比时间戳）

**实施设计（新会话按此落码）**：
1. **本地最后编辑时间戳**：upsertCloudData 时业务层记录本地 mtime（建议 PersistenceV2 key 如 'cloud-sync-local-mtime-flat'/'-tabs'，或模块级+落盘），这是下行仲裁的基准
2. **下行 handler 加仲裁**（ChatModel.ets 的 setupCloudDownlink 注册的 handler）：收到云端 (value, updated_at) → 云端 updated_at > 本地 mtime 才写回本地池；<= 则丢弃（本地更新，绝不回退）——旧/空树再也覆盖不了新树，PC 清零事故根除
3. **写回前备份**：被替换的本地池快照先存本地 PersistenceV2（key 'flat_pool_last_backup' 类），数据安全兜底（不写云端表，避免污染同步数据）
4. 注意坑：RDB autoSync 下行会由框架直接覆盖本地表行（业务层拦不住框架写表）——所以仲裁必须在 pullAndNotify→handler 链路里做在"写回业务池"这一步（框架表行被覆盖无所谓，业务池是唯一真相源，启动时从业务池恢复）
5. 回归场景（验收必测）：双端同开→A 建气泡→B 建气泡→互不覆盖不清零；A 建→B 删→时间戳新者胜
6. 版本 0.217.2 → 0.218.0（次位升级），两处版本号同步+一条龙+三台 bm dump

## ★★ 2026-10-10 深夜二次拍板（用户推翻 agent"两池粒度"初判，终版定案）

**粒度终案=实体级行级时间戳仲裁**（用户原话核心："你不能说整个气泡树……里面的每一个卡片、甚至对话……最小检测单位你自己看着办……以最新的那个时间戳为准"）：
- **不是池级整快照**（旧方案清零事故根源），也不是 C 方案三路合并（团队场景不需要）
- **RDB 表拆行：每个气泡节点一行**（key=`node_<nodeID>`、value=节点 JSON+归属池标记、updated_at=该节点最后编辑时间），上行单位=被编辑的节点行，下行仲裁=行级时间戳比较
- 效果：PC 改气泡1、Pad 改气泡2 → 两条更新都保留互不覆盖（不同行各赢各的）；同节点双端改=后写赢（个人用户场景可接受）
- **删除语义**：上行墓碑行（value 空+updated_at+deleted 标记）或独立 deletions 行，下行按墓碑移除节点
- **单词库/知识库未来上云同步时沿用同模式**（每词条/每卡片一行，独立时间戳）

**新设备场景安全论证（用户核心关切，2026-10-10 提出的验收场景）**：
- 场景：PC 编辑了大量数据 → 新买 Pad 装新 app（0 数据）→ 开云同步 → **PC 会不会被清空？**
- **答案：不会**。三重守卫：①**空不上行**——本地池/节点为空（0 数据新设备）禁止 upsert，新 Pad 只拉不推，PC 的云端数据纹丝不动；②时间戳仲裁——新 Pad 拉下行：云端 updated_at(大) > 本地 mtime(0) → 正常写回全量，Pad 秒得 PC 全部数据；③新 Pad 真正编辑后，也只有它编辑的那几行上行胜出，其余行不受影响
- **"空不上行"守卫是本场景的命门**：旧方案清零事故的机制=新/空设备无脑 upsert 空树覆盖云端——此守卫必须与行级仲裁一起落地，缺一不可

**实施注意**（在原四要点基础上修正）：
- 原"两池粒度"的 ①②③④ 要点中，仲裁基准从池 mtime 改为**行级 updated_at**（每节点行自带）；本地业务层维护各节点行的时间戳（编辑该节点时刷新）
- saveTree 链路改造：serialize 时 diff 出被编辑节点（或直接每次全量上行各行，行级 REPLACE 天然幂等——推荐后者，简单且正确性等价）
- 写回前备份保留（整池快照备份即可，不必行级备份）
