## 二、切库 bug 根因（修订版）：冒泡双发竞态

- 卡身翻面 onClick 挂在整个大 Column（含 pill 行、评分区）——ReviewWidgetCard.ets:377 热区覆盖 pill（:295）；
- ArkTS ClickEvent 冒泡且无 stopPropagation（项目 0.196.2 实锤）；
- **正面（flipped='n'）点 pill → sendSwitch + 冒泡 sendFlip 双 call 同时发出**；反面（flipped='y'）点 pill 卡身条件不满足、单发必好——行为不对称是投递层假设（call 5s 超时 / updateForm 1s 合并）解释不了的；
- 主进程两个 handler 竞态写 state：flip 后到 = 新库被翻成反面（「切库没反应/直接看到答案」体感真身）；
- 0.252.0 的「消费层空 onClick」物理上不可能挡冒泡（事件照样穿过）——这就是 0.252.0 修复无效的原因；
- **附带漏洞（三方均未覆盖）**：call 通道 handleWidgetRate 无任何时间戳闸——刷新未回时连点两次评分 = idx 跳两格丢卡。

## 三、修复三件套（替换原方案第一节）

1. **翻面热区收窄（结构根治）**：卡身 onClick 从大 Column 挪到正面题面 Column——pill / 评分区 / 反面音标从热区物理移出，冒泡双发在结构上不可能发生。
2. **全局动作门闸（兜底一切多发出 call）**：组件成员 `lastActionAt`，switch / rate / flip / continue / speak 五出口统一走 `gate()`（500ms 冷却只放行一个）——一次物理点击无论冒泡触发几个 onClick 只发一个 call；同时根治评分连点跳卡。
3. **置灰视觉反馈**：`@State locked` + setTimeout 1500ms 复位（卡片进程 setTimeout 有项目先例：pushWidgetState 0.252.1 起真机在跑）——锁窗内 opacity 0.4，用户有「已收到」感知。

诊断日志（验收后删）：宿主 EntryAbility Callee `widgetSwitch` / `widgetFlip` 入口各加 `hilog 'WGT' recv`——正面点切库若同时收到两条 recv=冒泡双发当场实锤；recv 数 < 点击数=投递层丢（原三方假设）。卡片 UI 文件不加日志（hilog 在卡片渲染进程支持无实锤，零风险设计）。

## 四、布局重构（照原方案第二节，全文执行）

- 正面：Blank + 标题居中 + 音标小字（不可点）+ Blank + 「点击查看答案」；onClick 挂此区（热区收窄落点）。

## 十一、风险点（含落码实锤修订）

- **落码实锤①（编译器白纸黑字）**：卡片渲染进程拒斥 `setTimeout` / `heightAdaptivePolicy` / `wordBreak`（`11706006 can't support form application`）——
  - 置灰视觉反馈**降级删除**（无复位路径；gate 门闸纯逻辑保留，主进程 300ms 延迟重推保证刷新及时）；
  - `heightAdaptivePolicy` 显式行删除（ArkUI 默认值即 MAX_LINES_FIRST，行为不变）；`maxFontSize/minFontSize/List` 编译通过保留；
  - `wordBreak` 删除（英文长词退默认断行，minFontSize 缩字+maxLines 多行下 "…" 概率大降，验收第 3 条把关）。
  - 教训：**卡片 UI 代码与 FormExtensionAbility 进程是两个编译目标**——pushWidgetState 里 setTimeout 跑得好好的（ExtensionAbility 进程），不代表卡片 UI 文件能用（form 渲染进程白名单更严）。
- **落码实锤②**：`ListItem {}` 漏构造括号会编译成乱码 ts（`Text(this) { }, : .title`）再报 es2abc 语法错——错误行号在中间产物不在源文件，定位看 `build/.../esmodule/debug_widget/` 产物。
- @State 置灰复位若遇进程冻结极端情况=多灰片刻，解冻自愈，无死灰路径（gate 重新放行时重置 locked）。——已随置灰删除作废。
- 存量 2×2 卡片删除规格后由系统按失效处理（原方案已裁定自然失效无崩溃风险，验收第 7 条复核）。
