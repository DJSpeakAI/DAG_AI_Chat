## 一、现象与嫌疑链（代码实锤）

- SP 账本双载体：本地 P2 key `siyi-points-v1`（PersistenceV2）+ 云行 `cfg:siyi-points`（RDB cloud_data，
  `mergeSiyiPointsRow` max/union 单调合并，ChatModel.ets:4065）。
- 上行链：SP 变动 → `scheduleRowFlush` → `upsertIfChanged` → `upsertRow`（**首拉闸门 rowInitDone 拦截**，
  CloudSyncUtil.ets:267）；下行链：`cloudSync()` resolve / dataChange → `reconcileWithRows`（缺片=整行丢弃+闸门不开+6 次 nudge）。
- 三条嫌疑（均可测试台实锤）：
  1. 云端 `cfg:siyi-points` 行缺失/过期（PC 上行链断——闸门曾长期未开时 SP 变动从未上行）
  2. P2 `siyi-points-v1` 单 key 水合失败（0.299.2 bug5 'huawei-account' 同族——盘值真/运行时恒 0）
  3. 启动时序：reconcile 完成前 UI 显示本地值（用户看到 0 的窗口期）

### 决定性实验链
1. **手机第三端裁决**：手机首登同账号 15 秒拉齐 **95 行（含 SP 行）**→云端确有行→**PC 下行选择性丢 cfg:siyi-points/cfg:stat-days 两行**（其余 8 类 93 行正常）。
2. **删库重建无效**：删 PC 全部 db*（含 naturalbase -dwr/-compare）→冷启→**0 行**（死锁：首拉不完成→闸门不开→flush 不写→永 0 行）。系统 hilog 抓到 DistributedDB SQLite Error[21] misuse（手机也有=系统噪音非根因）。
3. **卸载重装根治**：bm uninstall→装 0.299.2 signed HAP→冷启→**15 秒 95 行全量拉齐+SP 行到位+侧栏 2,000,000 SP 显示**。
   - 根因定性：**PC 设备的 naturalbase 注册态损坏（系统侧，删 app 数据不可清）→下行对特定行抑制；彻底卸载重装=清设备注册态=唯一解**。→ **华为工单核心素材**（对照实验数据全）。
4. 修复过程全自动化实录（dump 驱动 UI 链）：协议勾选框=**18x18 Image 无文本节点须点勾选行首**（行中心=《隐私政策》链接→误进全文页循环）；华为授权页勾选行左端+「同意并登录」；权限弹窗「允许」；GSD→云同步 Tab→开启。全程 uiInput click + displayId 15（PC 自由窗口）。

## 四、使用指引

1. **服务须重启生效**（改了 server.js+config.json；watchdog 未在跑）：DevEco Terminal
   `cd testing/console && sh 启动测试台.sh`（或 watch-server.sh 一次，此后 agent 改码 5 秒自动重启）。
2. 推荐排查顺序（用户在场配合）：**SP-AUDIT（定性主刀）→ SP-HYDRATION（水合实锤）→ SP-RESTART →
   SP-MONITOR → SP-GATE-BRANCH → SP-SIGNIN-CROSS → SP-COLD-FULL 最后跑（卸载重装破坏性）**。

   「跨端不一致」=max 合并未收敛（看行龄定位滞后端）。

## 六、人工审批项汇总（CloudSyncUtil 红线——用户拍板后转人工/专会话实施）

| # | 改动 | 方案（华为工程建议版） | 风险 |
|---|---|---|---|
| A1 | **防抖 3s→30s** | scheduleRowFlush 防抖窗口拉长，SP/词卡/知识库上行全链降频避限流 | 高频用户多端收敛变慢（30s 窗口） |
| A2 | **HLC 版本列** | updated_at 语义升级：高 52 位单调毫秒（max(now, lastCloudMax+1) 防回拨）+低 12 位设备序号（0~4095 首启随机持久化）——应用层裁决同毫秒，全端结果一致 | **Schema 红线**（updated_at 写入语义变更，非结构变更）；需新旧编码兼容期 |
| A3 | **dirty 对账列** | 表新增 dirty INTEGER 列（表列只增合规）：写置 1、手动 cloudSync 成功后清 0——上行丢失可观测 | 表结构变更+flush 链改造 |
| A4 | **CLOUD_FIRST 基准对齐** | 长期离线设备（>N 天）首拉先 SYNC_MODE_CLOUD_FIRST 云到端对齐再回 TIME_FIRST——杜绝僵尸行复活 | 与现有首拉闸门逻辑合并需谨慎设计 |
| A5 | **低频探测链路** | 前台切换时手动 cloudSync 探测一次，捕获 BusinessError+message 上报（autoSync 失败无通知——探测=唯一显式反馈） | forceCloudSyncNow 需导出错误（红线文件签名变更） |

**建议实施顺序**：A1（纯参数、收益立现、风险最低）→ A5（可观测性）→ A2/A3（账本正确性加固，需兼容设计）→ A4（场景加固）。
