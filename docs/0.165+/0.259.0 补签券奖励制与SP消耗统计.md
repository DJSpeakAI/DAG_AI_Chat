## 一、需求背景（用户口述归纳）

1. **补签卡改奖励制**：补签卡不要"购买"（原商业口径 1,000 SP/张，每月限 2 张），改成**升级奖励**——因为用户之前的努力（升级）而奖励的券，阶梯发放（一张、两张、三张）。
2. **券的展示入口**：账单页（资产区，与 SP 余额同屏，让"升级了"有获得感）。
3. **统计方案改造**：统计页加「SP 消耗量」（天/周/月）；两种 SP（充能/嘉奖）**合在一起统计，不分开**（用户已拍板倾向）。

## 三、方案 A：补签券（升级奖励制）

### 3.1 发放规则（阶梯，待拍板 Q1）

| 达成等级 | 累计学习天数 | 送券 |
|---|---|---|
| Lv2 司墨 | 7 天 | 1 张 |
| Lv3 司简 | 30 天 | 2 张 |
| Lv4 司理 | 90 天 | 3 张 |
| Lv5 司微 | 150 天 | 4 张 |
| Lv6 司玄 | 210 天 | 5 张 |
| Lv7 司天 | 240 天 | 6 张 |
| Lv8 司忆令 | 365 天 | 10 张（满级大礼，Q2 待拍板——Lv8 已有 SP 永久免费） |

- **发放时机**：`notifyLevelUp()` 内（单一收口——本端学习升级、云下行吸收升级两路天然全覆盖，0.217.2「多入口漏一环」教训前置规避）。
- **防重复**：SignInStore 尾部追加 `makeupGrantedLevel: number = 0`（已发券等级基线），只发「新达等级」的份额。
- **存量用户口径（Q3 待拍板）**：升级检测首次建立基线（lastLevel 0→N）时静默不弹不追发——老用户不突然多出一堆券，新机制从上线起算。

### 3.2 券的使用（补签续接连击）

- **可补日 = 昨天**（唯一补签日，最简防刷，Q6 待拍板）。
- **入口**：签到弹窗——断签态（昨天漏签 && 今天未签 && 持有券 > 0）显示「使用补签券 ×1 续接连击」按钮。
- **动作**：消耗 1 张 → 昨天记入已签集合 → **streak = 断签前 streak + 1**（续接语义，不重新计数）→ 今天再正常签到再 +1。
- **效果示例**：连签 10 天 → 昨天忘了 → 今天打开显示「连击已断」；用 1 张券补签 → 「连击已续接（11 天）」→ 今天签到变 12 天。**券的本质=一次"后悔药"，保护的是用户此前的坚持。**

### 3.3 存储与字段（Schema 铁律合规）

SignInStore（key `sign-in-v1` 不变）尾部追加三个默认值字段：

| 字段 | 类型/默认 | 用途 |
|---|---|---|
| `makeupVouchers` | number / 0 | 持有券数 |
| `makeupGrantedLevel` | number / 0 | 已发券等级基线（防重复发放） |
| `makeupDates` | string[] / [] | 已补签日期（防同一日重复补签） |

- 券跟随签到体系走**本地持久化**（同 signDates 语义——连击本来就是本地概念，多端各自一份、不合并，口径一致简单）。

### 3.4 展示入口（三处）

1. **账单页**：司忆点资产卡内加一行「补签券 ×N」（Q5 待拍板：资产卡内一行 vs 独立小卡）。
2. **签到弹窗**：正常态底部小字「补签券 ×N」；断签态显示补签按钮。
3. **升级弹窗**：升级瞬间展示「🎉 获得补签券 ×N」——奖励的仪式感放在升级这一刻（正是用户要的"因为努力而奖励"）。

### 3.5 文案同步（2 处）

- GSD:2928：「补签卡（1,000 SP/张，每月限 2 张）可续接连击」→「补签券由等级升级奖励获得，可续接连击」
- GSD:2888：「可用补签卡续接」→「可用补签券续接」（名称统一**补签券**，Q4 待拍板）

## 四、方案 B：统计页 SP 消耗（天/周/月）

### 4.1 数据层

- `StatDayEntry` 尾部追加 `spUsed?: number`（默认缺失读 0，Schema 铁律合规）。
- **埋点收口 = `consumeSiyiSp()` 函数内部**（单一收口：AI 回复完成、重生成、未来的两段式长回复等一切新扣点场景自动带上）——实扣成功后累加到当天行。
- ⚠️ **learnDays 口径保护（关键风险点）**：等级头衔 = 统计行数（有学习活动的天数）。SP 消耗埋点**只累加到已存在的当天行、绝不创建新行**——守住「行存在=当天有学习活动」不变式，杜绝"纯消耗虚增学习天数→误触 Lv8 免扣"的理论风险。实际场景 SP 消耗必然伴随 AI 对话（行已存在），零丢失。
- 云同步 `mergeStatDaysRow` 加一条 max 合并（照 siyi 字段抄）——spUsed 单调递增，max 语义自洽，双端一致。

### 4.2 UI 层

- 统计页加**第五卡「SP 消耗」**：
  - 累计消耗：X SP
  - 今日 / 昨日：X / X
  - 本周 / 上周：X / X
  - 点击卡片 → 柱状图切「SP 消耗」序列（复用现有 selectedMetric 机制，日/周/月/年全维度可看）
- **两种 SP 合并展示（用户已拍板）**：消耗时本来就是"先嘉奖后充能"一锅扣，用户视角 SP 就是一种点数；想看两池明细去账单页资产卡——统计页看流量、账单页看存量，职责清晰。
- 大数字用千分位；卡样式复用现有 SURFACE_NODE 卡定式（UI_GUIDELINES 组件规格）。

### 4.3 测试数据（顺手）

统计页 360 天 seedTestData 顺手造 spUsed 值——柱状图验收用；上线前随 seed 一起删（既有约定）。

## 六、风险点

1. **learnDays 虚增**（最大风险）→ 已用「只累加已有行、不建新行」守卫根除（见 4.1）。
2. **多端重复发券**：券本地存储，每台设备各自基线各自发 → 单设备最多 1 份额度，跨设备不合并（与连击本地语义一致）。账单页看的是本机持有量。
3. **补签 × 调试日期偏移**：DebugDayOffset 基建已有，补签行为可真机快测（不用真等断签）。
4. **云同步 max 合并**：spUsed 只增不减，无双端写冲突风险。

## 八、验收标准（裁决后落码用）

1. 升级弹窗出现「获得补签券 ×N」，账单页资产卡数量同步。
2. 断签后签到弹窗出现补签按钮 → 用券 → 连击续接（断签前 streak+1）→ 今日签到再 +1。
3. 同一断签日不能重复补签；券为 0 时按钮隐藏。
4. 统计页第五卡显示累计/今日/本周消耗；点击切图表，日/周/月/年四档数据正确。
5. AI 对话后账单页 SP 余额减少量 = 统计页当日消耗增量。
6. 双端云同步后统计页 SP 消耗数据收敛一致（max 合并）。
7. 学习天数（等级头衔）不因纯 SP 消耗产生新行而虚增。
