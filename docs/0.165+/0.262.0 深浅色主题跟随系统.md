## 三、核心决策：深色模式 = 现有暗紫原样（推荐方案甲），不另造第二套深色

**这是用户最纠结的问题，先给结论再给理由。**

### 推荐方案甲（本方案采用）：深色 = 现暗紫，浅色 = 新设计一套

- **深色模式 = 现在的暗紫 token 原封不动**。现有暗紫就是一套完整、成熟、被用户长期验收的深色主题。
- **浅色模式 = 新设计一套浅色 token**（第六节给初值表）。
- 「跟随系统」= 系统深→用现暗紫，系统浅→用新浅色。**总共只需要两套色表**。

理由：
1. **品牌延续**：主紫 `#7C4DFF` 是品牌锚点。深浅两套共享同一主紫，切换模式时"还是这个 app"的感觉不丢。若另造一套深色（比如换主色相、纯黑 AMOLED 底），品牌割裂。
2. **用户已验收**：现暗紫 14 token 来自 Pixso 设计稿、经几十个版本打磨验收（UI_GUIDELINES 全沉淀）。另造深色 = 把用户已认可的视觉全部重新审一遍，高工作量、高风险、收益存疑。
3. **华为生态惯例**：HarmonyOS 应用深色模式通行做法 = 品牌色深色变体；"主题感"靠品牌色贯穿，不靠每套模式换色相。
4. **工作量减半**：两套色表（现暗紫 + 新浅色）vs 三套色表（现暗紫基线 + 新深色 + 新浅色）。

### 备选方案乙（不推荐，仅供评审挑战）：另造一套深色

例如纯黑底（AMOLED 省电）或去紫灰黑底 + 换主色。**不推荐理由**：违背品牌延续；用户没表达对现暗紫的不满；三套色表维护成本高。若 DeepSeek/豆包有强论据支持乙，请给出具体场景（如华为审核对深色对比度有硬指标），否则维持甲。

> **待评审 Q1**：是否认同"深色=现暗紫原样"？有没有"必须另造深色"的硬理由（上架审核/无障碍对比度）？

## 四、总体方案：三态主题

### 4.1 模式定义

```
themeMode（用户意图，持久化）: 'system' | 'dark' | 'light'，默认未选择
effectiveDark（运行时生效态）: system→按系统 colorMode 换算；dark→true；light→false
```

- 持久化 key：**`theme-mode-v1`**（PersistenceV2，新 key 不碰存量）。
- **未选择态**（key 不存在，含存量用户升级上来的）：首启弹选择弹窗（见第七节）；弹窗落定前 UI 默认 = 暗紫（现 UI 原样，弹窗自身也用暗紫渲染，与协议弹窗一致）。
- 存量用户升级后 key 同样不存在 → **也会弹一次选择**（他们从未选过，给一次知情权，只弹一次）。

### 4.2 切换链路（全部即时生效，无需重启）

```
用户改模式（设置/首启弹窗）
  → PersistenceV2 落盘 themeMode
  → AppTheme.mode 更新 → effectiveDark 重算 → palette 全表刷新（@Trace 逐字段）
  → 全 UI 引用点响应式重绘（@ObservedV2 依赖链）

系统深浅色变化（仅 mode='system' 时）
  → EntryAbility.onConfigurationUpdate(config.colorMode)
  → AppTheme.refreshFromSystem() → palette 刷新 → 全 UI 重绘
```

## 五、技术施工方案

### 5.1 架构：AppTheme 运行时主题源（复活改造）

新增 `entry/src/main/ets/common/AppTheme.ets`（**DesignTokens.ets 保留为字号/圆角/字体 token 的真相源不动**，色值职责移交 AppTheme；也可两文件合一，见待评审 Q7）：

```typescript
// AppTheme.ets — ★ 0.262.0 运行时主题源（唯一色值真相源，取代 DesignTokens 色值段）
// 模式：system（跟随系统）/ dark（暗紫）/ light（浅色）；未选择=按 dark 渲染
import { AppStorageV2, PersistenceV2 } from '@kit.ArkUI';
import { ConfigurationConstant } from '@kit.AbilityKit';

export type ThemeMode = 'system' | 'dark' | 'light';

const DARK_PALETTE = { bgApp: '#120B1F', bgNav: '#1A1030', ..., brandPrimary: '#7C4DFF', ... };  // = 现 DesignTokens 暗紫值原样
const LIGHT_PALETTE = { bgApp: '#F7F5FA', bgNav: '#FFFFFF', ..., brandPrimary: '#7C4DFF', ... }; // = 第六节初值表

@ObservedV2
export class AppTheme {
  @Trace mode: ThemeMode = 'system';
  @Trace isDark: boolean = true;          // effectiveDark（未选择期=true 暗紫兜底）
  // ── 全色值 @Trace（字段名 camelCase，与原 DesignTokens 常量一一对应）──
  @Trace bgApp: string = DARK_PALETTE.bgApp;
  @Trace bgNav: string = DARK_PALETTE.bgNav;
  ...（14 token + EDGE 两色 + 语义色 + REVIEW 三档 + CODE 五色 + OVERLAY 两档，全部字段化）

  applyMode(m: ThemeMode, systemDark: boolean): void { /* 落盘 mode + 重算 isDark + 整表赋值 */ }
  refreshFromSystem(systemDark: boolean): void { /* 仅 mode='system' 时生效 */ }
}

export function connectAppTheme(): AppTheme {
  return AppStorageV2.connect(AppTheme, 'app-theme-v1', () => new AppTheme()) as AppTheme;
}
// 用户选择的持久化（PersistenceV2 独立小类，key 'theme-mode-v1'——AppStorageV2 不落盘故分开）
```

要点：
- **运行时态与持久态分离**：AppTheme（AppStorageV2，会话内同实例）管渲染；ThemeModePersist（PersistenceV2 `theme-mode-v1`）管记忆。冷启动 EntryAbility 读持久化 + 系统 colorMode 初始化 AppTheme。
- **两份 const 色表集中一处**，浅色表改动只动一个文件。
- EntryAbility 里残留的旧 `ThemeStore` 死类删除，防两个主题源打架。

### 5.2 系统深浅色感知

- 冷启动：`EntryAbility.onCreate` 读 `this.context.config?.colorMode`（无值时默认按深色兜底）。
- 运行中：**重写 `onConfigurationUpdate(config)`**（UIAbility 系统回调，系统深浅色/语言变化触发），读 `config.colorMode === ConfigurationConstant.ColorMode.COLOR_MODE_DARK`，仅 `mode='system'` 时调 `refreshFromSystem()`。
- 参考：EntryAbility 现无该回调，新增无冲突。

### 5.3 全量替换模式（19 文件机械改造）

| 改造前 | 改造后 |
|--------|--------|
| `import { BG_APP, BRAND_PRIMARY } from '../common/DesignTokens'` | `import { connectAppTheme } from '../common/AppTheme'` + 成员 `theme: AppTheme = connectAppTheme()` |
| `.backgroundColor(BG_APP)` | `.backgroundColor(this.theme.bgApp)` |
| `if/三元` 里的色值引用 | 同上直接换属性访问 |

- 字号/圆角/字体常量（FONT_SIZE_*、RADIUS_*、FONT_INTER*、NODE_W 等）**不动**，继续从 DesignTokens import（两 import 并存）。
- 替换量大但纯机械；**必须分文件逐个编译验证**（见 5.6 分批施工）。

### 5.4 关键 ArkTS 雷区（本项目已踩过的坑，施工必避）

1. **带参 @Builder 按值传参丢响应式（最高危）**：`@Builder card(bg: string)` 里用参数色值，主题切换时**不会重绘**。改造时必须让 @Builder **体内直接访问 `this.theme.xxx`**，禁止把色值当 string 参数传进 @Builder。排查方法：全局 grep 带参 @Builder 中使用色值常量的调用点，逐个内联。
2. **@Trace 依赖链**：凡 `@Computed` 引用的源状态必须正确挂装饰器（本项目 windowMode/isTablet 曾三踩）；AppTheme 成员一律 @Trace。
3. **一处坏全文件崩**族谱（注释吞签名/孤儿属性/闭合错位/import 夹语句）：大范围文本替换后必须本地编译，禁止攒到最后一把梭。
4. import 之间禁夹语句（arkts-no-misplaced-imports）：新增 connectAppTheme import 插 import 区末尾。
5. 生命周期钩子禁止重复定义（aboutToAppear 曾二踩）。

### 5.5 启动页与系统层

- `start_window_background`：base 改浅色初值 `#F7F5FA`，dark 保持 `#120B1F`——资源限定词机制免费获得"跟随系统"。
- **已知瑕疵（接受，不修）**：用户强制深色 + 系统浅色时，冷启动启动页会先白一闪再进暗 UI（资源限定词只跟系统走，无法感知 app 内选择）。主流 app 均如此，注明即可。
- 若 Index/各页有 `window.setWindowSystemBarProperties`（状态栏色）调用，需跟随 effectiveDark 调整（施工时全局 grep 确认，现状疑似无调用）。

### 5.6 分批施工（防一次性大爆炸）

- **批 1（基建+入口）**：AppTheme.ets + EntryAbility（onConfigurationUpdate/删旧 ThemeStore/冷启动初始化）+ PersistenceV2 + 设置入口（第八节）+ 首启弹窗（第七节）+ 本批编译过。此时 UI 仍全暗紫（token 未迁移，AppTheme 先跑通链路）。

## 十、风险与预案

| 风险 | 概率 | 预案 |
|---|---|---|
| 19 文件大替换引发全文件解析崩（族谱雷） | 高 | 逐文件改逐文件编译；报错超 100 个先查闭合/孤儿代码，勿死盯报错点 |
| @Builder 参数色值丢响应式（切主题局部不刷新） | 高 | 5.4-1 强制规范 + 验收 6 专项 grep + 真机三态切换逐页巡检 |
| 浅色对比度不达标（辅助紫/弱文字） | 中 | 初值表已加深；真机自查 + 评审挑刺 |
| 系统弹窗（权限弹窗等）与浅色不协调 | 低 | 系统弹窗跟系统深浅走，不归 app 管，注明即可 |
| 桌面卡片（WidgetHostBridge 体系）颜色不同步 | 中 | 桌面卡片有自己的渲染进程——**一期不跟主题**（保持现深色卡片），文档注明；二期评估卡片深浅适配 |
| 云同步/埋点等非 UI 模块引用 DesignTokens 色值（如 ChatModel） | 低 | ChatModel 引用一并迁 AppTheme（纯字符串用途，无逻辑耦合） |
