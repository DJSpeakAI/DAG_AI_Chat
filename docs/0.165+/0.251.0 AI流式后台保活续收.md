# 0.251.0 AI 流式后台保活续收（切后台不断流）

> 2026-10-18 立项实施。用户拍板：「用户等 AI 长回复/圈注提炼时切后台是高频场景，回来必须看到已生成的完整内容」。0.153 时代「切后台主动 abort AI」策略整体反转。
> 版本：0.251.0（versionCode 1000308）；0.250.0 敏感词预过滤已占用顺延。
> 外部讨论稿：桌面 123.txt（dataTransfer 方案+过审三原则，已消费）。

## 一、需求与背景

- 现状问题：①提炼链（划词入知识库/屏幕圈注）一切后台就被 0.153 的 `onAppBackgroundChange @Monitor` 主动 cancel；②聊天长回复/查词浮窗虽无主动断，但鸿蒙对后台应用掐网络（0.153/0.206.2 真机实证），SSE 被系统杀掉报错。
- 用户场景：AI 生成 1~4 分钟（未来两段式钩子模式更长），等待期切后台是必然行为，回来面对断流/半截回复=体验灾难。
- 结论：申请 **dataTransfer 长时任务**保活续收（用户触发、进度可见、结束即停三原则过审，官方 Background Tasks Kit 规范）。

## 二、方案（咽喉收口设计）

**核心架构决策：保活逻辑全部收口在 ApiClient.streamChat 内部**——streamChat 是四条 AI 链（聊天 streamChat / 查词 queryWord / 划词提炼 queryKnowledge / 圈注提炼 queryKnowledgeFromImage）的唯一咽喉（后三者内部复用 streamChat），acquire/release/touch 在函数内闭环，**页面层零侵入**，未来新增 AI 调用点自动获得保活。

### 新文件 utils/AiStreamGuard.ets
- `acquireAiStream(scene)` → 令牌；首请求启动长时任务（`startBackgroundRunning(ctx, ['dataTransfer'], wantAgent)`，点击通知拉回应用）+ 3s 进度定时器；末请求 stop（**结束即停=过审红线**）。
- **实况窗进度通知**（官方条款实锤：①DATA_TRANSFER 进度超 10 分钟未更新→任务被系统取消；②进度通知必须实况窗 downloadTemplate+typeCode 8+任务返回的 notificationId 复用）：每 3s 更新——进度值=elapsed/150s 映射 0~99（时间驱动，思考期无 chunk 也持续更新=活性保证），文案=「已接收 N 字/已等待 N 秒」。
- **完成提醒**：独立本地通知（SOCIAL 槽位带提示音——长时任务通知本身无提示音，官方实锤），仅后台时发（前台有 UI 不打扰），点击拉回应用；固定 id 覆盖不堆叠。标题=「{场景}已完成/已中断」。
- **90s 看门狗**：无任何字节（chunk/reasoning/心跳）90 秒判死流→cancel+onError 中文提示+释放任务（比 ApiClient 300s readTimeout 提前止损；阈值留 30s 余量防深度思考慢启动误杀）。
- **通知授权时机（用户拍板）**：第一次发起 AI 请求时场景化申请 requestEnableNotification（不一打开就弹；拒绝后降级无"叮咚"，内容照常落盘不丢）。

### ApiClient.streamChat 改动
- 入口 acquire；三出口（onDone/onError/cancel）+ 看门狗死流全部 guardFinish 幂等收口。
- dataReceive 每字节到达 touch（心跳也算活——不误杀收 keep-alive 的连接）；texts/reasonings 字数累计进进度文案。
- 终结时后台则发完成/失败通知；新增可选尾参 `sceneLabel`（查词='AI 查词'、提炼='AI 提炼'、圈注='AI 圈注提炼'、默认='AI 回复'）。

### 其他挂点
- **EntryAbility**：onCreate `initAiStreamGuard(this.context)`；onForeground/onBackground `setAiStreamBackground(false/true)`。
- **module.json5（红线文件，用户授权）**：EntryAbility 加 `"backgroundModes": ["dataTransfer"]`——仅此一行；`KEEP_BACKGROUND_RUNNING` 权限 0.204.1（桌面卡片）已声明，零新增权限。
- **ChatPage**：删 0.153 的 `onAppBackgroundChange` 主动中断 @Monitor + appLifecycle 字段 + import（死代码清理）；超时文案「后台网络超时…」改为「网络连接超时」（不再归因切后台）。

## 三、★ SP 扣点军令（钩子模式开发必读——用户 2026-10-18 拍板，本节为指定记录点）

1. **两段式调用 SP 累加**：未来长回复两段式（①DeepSeek 深度生成高质量内容 → ②拿①的结果再申请一次 AI 做钩子模式加工，两次串联不是三次）——**两次调用的 token 消耗必须累加实扣**，沿用 0.248.7「展示多少扣多少」军令，两次 onDone 累计后一次性落账（consumeSiyiSp 同公式），禁止只扣其中一段。
2. **凡 AI 交互必扣必展示**：任何新增 AI 交互点（包括但不限于司忆区问 AI、钩子模式第二段、未来的翻译/搜索增强等）都必须：①计入 SP 实扣（spCostOf 同源公式，调价改一处）；②有 SP 消耗展示（形态可按场景适配——聊天气泡走感叹号明细弹层，轻量场景可走 toast/角标，但**禁止无展示的隐性扣点**）。对外文案禁出现 token 字样（防反推成本，0.247.3 军令）。

## 四、风险与边界

- **系统一致性校验**：官方 FAQ 实锤后台长时任务有一致性校验（校验任务类型与实际行为一致）；我们流式收字节=真数据传输，实况窗 3s 更新=进度可见。60 秒校验数字为社区口径非官方条款（123.txt），未采信为设计依据。
- **用户杀进程/系统极端回收**：长时任务也救不了，回来看到半截内容（已实时落盘，0.244.0 写穿机制，数据不丢）。
- **PC(2in1)**：长时任务申请失败静默降级（PC 后台通常不挂起，实际影响小）。
- **通知被拒**：无"叮咚"无进度通知，但传输与落盘不受影响。
- **123.txt「10 分钟首更新」条款已官方核实为真**（DATA_TRANSFER 枚举表原文：超过10分钟未更新进度任务被取消）——实况窗 3s 周期远低于红线。

## 五、验收标准（用户真机自测——生命周期后台场景测试台无注入/通知断言通道，不接用例，0.247.4 手势先例同款豁免）

1. 手机/Pad：发长回复→切后台→通知栏见「AI 回复中·已接收 N 字」实况窗进度→完成后「叮咚」+「AI 回复已完成」通知→点通知拉回应用→消息完整。
2. 屏幕圈注/划词提炼：同上场景，弹窗回前台时草稿已填好。
3. 前台正常使用零变化（无通知打扰）。
4. 请求结束（含取消/报错）后通知栏任务通知消失（结束即停）。
