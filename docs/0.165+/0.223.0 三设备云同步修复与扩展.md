# 0.223.0 三设备云同步修复与扩展

> 2026-10-12 立项。用户需求：①修复手机（畅享 90 Pro Max）不掉队的三端同步；②修复同步后气泡树连线/样式异常；③把单词库+知识库（含文件夹、复习进度、标签）全部纳入云同步。

## 一、CLI 诊断实录（问题①根因，全部实锤）

### 1.1 设备与版本
- 三台全部在线、应用全部 1000225（v0.222.22）——排除版本落后。
- 手机 `cloud-sync-switch` 落盘值 `{"enabled":true}`（PersistenceV2 persistent_storage 直读）——排除开关没开。
- 三台 `atm dump` DISTRIBUTED_DATASYNC grantStatus 全一致（已授予）——排除权限。
- 手机应用进程 13:32 起存活 11.5h（用户确实开着）。

### 1.2 数据真相（sqlite3 直读三台 dag_chat_cloud.db）
- PC 与 Pad：flat_pool 同为 `1791736964736 / 1950B`（时间戳字节级一致 = 今晚 00:42 双向同步正常）。
- 手机：flat_pool 停在 `1791717729881 / 1298B`（今晚 19:22 自己写的旧版本）——**云端新版本从未到达手机本地 RDB**。
- 手机 PersistenceV2 持久化文件 mtime = 19:22 后纹丝不动（下行从未写池）。
- 三台 `.db-compare` 时间戳一致 19:20（当时同步轮全员参与）；00:42 的轮次只有 PC/Pad 参与，手机缺席（当时后台/冻结）。

### 1.3 根因（架构缺陷，非环境问题）
现链路下行完全依赖**系统自动触发的端云同步轮**（autoSync 系统调度）+ dataChange 事件：
1. 手机错过 00:42 的同步轮（后台/冻结，华为冻结激进：切后台 1 秒即 Freeze——0.204.1 已入档）。
2. **应用回前台无任何主动拉取**：EntryAbility.onForeground 只做埋点补发；initCloudDb 幂等守卫（initPromise 非空直接 return）、activateCloudSync 幂等守卫（cloudSyncActive）——热启动回前台零动作。
3. `pullAndNotify` 只查**本地 RDB 表**（框架没下载过 = 永远查不到新数据），全代码无一处调用 `rdbStore.cloudSync()` 手动触发。
4. 结论：手机要等到「下一次冷启动 + 恰好有系统同步轮」才能追上——用户观察到「就是不同步」。

API 实锤（SDK d.ts 5814-5876 行）：`rdbStore.cloudSync(mode: SyncMode, tables: string[], progress: Callback<ProgressDetails>): Promise<void>`，云模式枚举 `SYNC_MODE_TIME_FIRST`（最新修改时间优先，与 0.218.0 仲裁「最新编辑者胜」语义一致）。

## 二、问题②根因（连线/样式异常，代码走读实锤）

下行写池链路 `refreshWorkspaceFromPools()`（ChatModel.ets 1341）置 `store.needsRelayout = true`，两处消费（BBTreeCanvas 1601 / 1861）一律 `autoLayout() + fitViewport()`：
- **缺陷 a（连线错乱）**：用户正看画布时下行到达 → nodeList 整体替换 → @Trace 触发气泡重渲染，但连线是 **Canvas 命令式绘制**（无状态绑定），redrawEdges 无人调用 → 连线停留在旧节点旧坐标 =「连接线有问题」。
- **缺陷 b（样式不一致）**：autoLayout 把**云端同步过来的原始坐标全部丢弃重排** → Pad 显示的是自己的自动排版而非 PC 的手动布局 =「样式和 PC 不一样」。更糟：autoLayout 末尾 saveTree → 重排结果又上行 → 污染 PC 端布局（布局乒乓毁灭链）。

## 三、问题③现状

单词库（PersistenceV2 key 'word-bank'：WordItem[] + WordFolder[]）/ 知识库（'knowledge-bank'：KnowledgeCard[] + KFolder[]）与云同步**完全无关**——upsertCloudData 全部调用点只覆盖 flat_pool/tabs_pool。复习进度（strength/reviewCount/lastReviewAt/nextReviewAt）、标签、文件夹、图片全部只在本机。

## 四、修复/扩展设计

### 4.1 问题①修复：三个强制同步触发点（新增 CloudSyncUtil.forceCloudSyncNow）
- `activateCloudSync()` 末尾：setDistributedTables 后立即 `cloudSync(SYNC_MODE_TIME_FIRST, ['cloud_data'])`（激活即追赶，替代"只查本地"的 pullAndNotify 语义）。
- `EntryAbility.onForeground()`：调 forceCloudSyncNow（回前台=最可靠追赶点，与 0.206.2 埋点补发同款结论；云端有新数据时框架下载 → dataChange → 既有下行链路接管）。
- `onBackground` 前顺路触发一次（本机未上行的编辑借机推走，本地下行已死但上行碰运气）。
- 守卫：cloudSyncActive=false / 未登录同步未开 → 静默跳过；失败静默（下次前台再试）。

### 4.2 问题②修复：下行保坐标 + 连线即时重绘
- BubbleTree 新增 `@Trace needsCloudRedraw: boolean = false`（尾部追加，Schema 铁律）。
- `refreshWorkspaceFromPools()`：flat/tabs 两分支改置 `needsCloudRedraw = true`，**不再置 needsRelayout**（对端坐标是真相，绝不再 autoLayout 重排——同时斩断「重排→saveTree→上行→污染对端」乒乓链）。
- BBTreeCanvas：`@Monitor('store.needsCloudRedraw')` 即时消费（画布在屏时：redrawEdges + fitViewport，保留同步坐标）；onShown 兜底消费同语义。树为空时回落 autoLayout（空树无坐标可保）。
- 模式切换等本机路径 needsRelayout 语义原样保留，互不干扰。

### 4.3 问题③扩展：word_pool / knowledge_pool 快照行（复用既有快照行模式 + 备份序列化线）

**上行**：
- 新增 `CloudSyncBridge`（utils）：`snapshotWordPool()/snapshotKnowledgePool()` 复用 BackupUtil wordToPlain/cardToPlain 序列化（0.205.4 已解决 @ObservedV2 不可枚举序列化问题，内外备份同一流水线）+ folders + payload version。
- 触发点：onBackground（退后台快照上行——本地 RDB 写入不受后台网络限制，推云交给框架/下次前台 forceSync）+ onForeground forceCloudSyncNow 前 + 单词/知识库关键写点（评分/增删改后防抖 3s，可选加强）。

**下行**（handler 扩展两个 key）：
- 时间戳仲裁：CloudSyncArbiter **尾部追加** `mtimeWord/mtimeKnowledge`（Schema 铁律：只追加，旧字段不动）。
- **条目级合并（本方案核心，用户拍板项见第五节）**：WordItem/KnowledgeCard **尾部追加 `@Trace mtime: number = 0`**（每条最后编辑时间）。合并规则=按 id 并集，同 id 取 mtime 大者；文件夹同款（KFolder/WordFolder 尾部加 mtime）。
- 删除传播：payload 带 `deleted: Record<id, mtime>` 墓碑表；合并时墓碑 mtime > 存活条目 mtime → 不复活；本地删除时记墓碑（写点：两库的删除确认链路 + deleteFolderCascade 等约 6 处）。
- 写回：合并结果重建 @Type 实例数组整体替换 store.words/store.cards（@Trace 触发全部页面自动刷新——0.222.x 已验证数组替换是可靠刷新模式）。
- 空不上行守卫：复用 upsertCloudData 既有守卫（空库快照禁止上云，0.218.0 清零事故命门）。

**写池后不回环**：与 flat_pool 同款纪律——下行写池绝不调 upsert；本机编辑 mtime 推进即天然挡回声。

## 五、开放决策点（需用户拍板）

**条目冲突粒度**（多端同时编辑同一张卡/同一个词时的取舍）：
- **方案 A（推荐）：条目级 mtime 仲裁**——同 id 条目双端都改过时，最后编辑者胜；双端各改各的卡（不同 id）时全部保留。代价：每条带 mtime 字段 + 写点埋 mtime（~15 处小改动）。
- **方案 B（最简）：池级时间戳 + 条目并集云端胜**——不加 mtime，下行时同 id 一律云端覆盖。代价：A 设备改卡 X、B 设备改卡 Y 时，后上传者的池会抹掉对方对 X/Y 的修改（丢并发编辑，单用户多设备场景低频但真实）。

## 六、风险点
1. `@Monitor` 嵌套路径真机可靠性（0.222.x 教训：@Computed 间接链真机不可靠）——needsCloudRedraw 用 @Monitor 直读单字段（已验证模式：0.201.3 onStateChange 同类），并保留 onShown 兜底双保险。
2. PersistenceV2 老数据无 mtime 字段 → 默认 0，首下行全量云端胜（等于现状快照语义，无回归）。
3. 图片 base64 体积：knowledge_pool 快照可能较大（9 图上限+压缩已做 0.211.1）——云端单行 value 上限需实测（当前 1950B 经验外推；超限兜底=快照失败静默留待下次，绝不阻塞本地）。
4. 墓碑表只增不减 → 长期膨胀；上限 500 条 FIFO 裁剪（足够覆盖误删恢复窗口）。
5. 云端 AGC cloud_data 表结构不变（仍是 key/value/updated_at 快照行）——**零云侧改动**，纯端侧升级（规避 AGC 控制台操作风险）。
6. dataChange 在 forceCloudSync 下载完成后是否可靠触发 → 用 cloudSync 的 progress 回调（SYNC_FINISH）后主动 pullAndNotify 兜底，不押注单一事件。

## 七、验收标准
1. 三台任意一台改气泡树（含手动拖动布局）→ 另两台 10s 内（前台）同步且**坐标与源端一致、连线正确**。
2. 手机杀进程冷启动/后台热启动回前台 → 30s 内追平云端最新（flat_pool 时间戳一致）。
3. 手机加词+评分 → Pad 进单词库（触发快照/前台）后可见该词及进度；反向同。
4. 知识卡三端同步：新建（含图片/标签/文件夹归属）、编辑、评分进度、删除（墓碑）全链路一致。
5. 单词库/知识库文件夹（含层级）三端一致。
6. 空库设备不被云端旧空快照清库（空不上行守卫 + 仲裁）。
7. 版本 bm dump 实锤 1000226 三台齐装。

## 八、0.223.1 / 0.223.2 测试实录（2026-10-12 凌晨，CLI 全自动双向验证）

**测试环境**：用户卸载三台应用（清空本地），AI 全自动重装+UI 自动化（uitest dumpLayout+click/node 解析）驱动。用户手动登录 Pad/手机华为账号；PC 办公占用暂缓。

**实测通过项**：
- ✅ 手机（畅享90 Pro Max）激活链：atm perm 预授权 + 边栏头像静默重授权（系统账号已登录时免交互）→ AppConfirmDialog「开启云同步」可注入点击
- ✅ 全新安装恢复：Pad 拉取四池 → 云端「你好」树落地画布（0.223.2 修复后）
- ✅ 正向传播（手机→Pad）：手机 ChatPage 被动复习（NLP/Neural/SOLID 戳 mtime）→ 3 秒防抖 → 闸门放行上云 → Pad 持久化词库出现手机的 reviewCount/mtime/nextReviewAt（逐字段实锤）
- ✅ 反向传播（Pad→手机）：Pad 复习页评「尚可」（Machine Learning strength:0.5 + 排期）→ 上云 → 手机持久化词库同步到该进度
- ✅ 首拉闸门：poolsInitDone 落盘实锤、被闸变更不丢（下轮快照重上）
- ✅ forceCloudSyncNow 诊断链路（cloudSync resolved → 四池拉取 → initDone）
- ⚠️ 删除墓碑传播：UI 注入被 0.200.0 Button 限制卡住（多选工具条「删除(N)」真 Button 不响应注入、滑动/长按在 Pad 无效）——逻辑已代码审阅未实测，留待用户真机一键验证

**测试中发现并修复的 Bug**：
1. **0.223.1 首拉闸门**（严重）：全新安装自动播种预置数据 → 被动复习触发防抖上云 → TIME_FIRST 本地新写入胜出 → **云端真实数据行被预置种子整体替换**（实测：word 2900B→2474B、knowledge 34KB→14.7KB、flat 3240B→487B 全被顶掉）。修复=arbiter 尾加 poolsInitDone，forceCloudSyncNow 四池拉取完成后解锁，此前一切池上行被闸。教训：**空不上行守卫只挡空数据挡不住非空种子——「防清零」要从内容判升级为时序判**。
2. **0.223.2 空池合并**（中）：unionMergeFlatPool 对本地空串（全新安装 PersistData 默认 ''）反序列化 null → 保守分支放弃合并 → **新设备从云恢复整棵树断裂**（Pad 实测 0 个气泡）。修复=空串直接采纳云端。

**遗留观察（非阻塞）**：
- onBackground 无条件快照会造成「未变更也上行」的行时间戳churn（union 合并保证正确性，仅效率损耗）——后续可加脏标记优化
- 锁屏/冻结会停上传任务（StopUploadTask）——回前台 forceSync 补推，属预期行为
- CLI 启动 MateBook 应用窗口零尺寸（aa start 后窗口不渲染，任务栏有图标）——手动点图标正常，不阻塞
- SQLite「database schema has changed」(17) 瞬态报错——框架自动恢复，查询成功，无需处理
