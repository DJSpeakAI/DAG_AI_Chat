## 三、用户报障（原始口径）

1. **模型别名**（0.238.0/0.238.1 功能）：设置→API 配置→输入别名（跟随供应商下模型一一对应）。不点保存→别名一直在；**点保存→关 APP→重开→别名没了**。（手机实测报障，Pad 同样复现）

## 四、根因分层

- **L1 表象**：别名字段 modelAlias 是 0.238.0 加到 ApiConfig 的尾部新字段，key 'api-config-v4' 当时同步新换。实测：**写盘正常（落盘 JSON 有值）、重启读恒空**（同实例 model/provider 回显正常、唯独它空）——即项目史上 0.143/0.190/0.224.1/0.238.0 四次「新字段挂旧 key 读丢」的读侧形态。项目历史 playbook = 换新 key，前四次都管用，**这次失灵**（见 L2）。
- **L2 黑洞（真正的时间黑洞）**：换 key 过程中真机实锤 PersistenceV2 多个反直觉行为（证据链见下节）：
  - **B1 盘值被冷启工厂值回滚**：带 factory 的 connect，盘上已有数据，冷启后实例值=工厂计算值而非盘值（用户保存的华为档被回滚成火山旧档）。
  - **B2 嵌套 connect 毒害水合**：在 A key 的 factory 内 connect B key，B 实例整个会话读不到盘值（盘上数据完好）。
  - **B3 行为自相矛盾**：同一份代码某些冷启配置存活、某些冷启被重置（中间隔着版本安装/不同 key 出生方式）；同为「纯 new factory + 顶层 connect」的 key（model-alias-v1 等）**全天 100% 可靠**。
- **L3 掩盖因素**：loadBuiltinApiConfig 每次启动把空 apiKey 回填内置 Key——「Key 被重置」长期被掩盖（用户配置一直等于默认值时，重置结果==现状，无感）。

## 八、测试台工程坑（新会话 AI 必读，别再踩）

1. **`uitest uiInput inputText` = 纯追加**（X1+Y2=X1Y2）；**无删除通道**：keyEvent 67(DEL)/组合键 113 29(Ctrl+A)/双击选区替换全部无效（TextInput 编辑不吃注入）。清空字段不可自动化——用例用「献祭模型」法（测试残留留献祭模型名下）。
2. **保存按钮随 IME/滚动位移**：必须 dump 实时定位（禁固定坐标）；且点击可能间歇落空——保存后必须有「盘值生效校验」（grep provider）+重试。
3. **提供商高亮判定**：品牌紫在父容器（文字节点 bg 恒 #00000000）——用「品牌色容器(#FF7C4DFF) bounds 包住哪家文字」的 containment 法。
4. **BusyBox grep BRE 量词上限 256**：`.\{0,900\}` 整模式失效恒空输出；用 ≤240。
5. **假绿两起教训**：固定短标记（AKT）会被历史残留命中；唯一时间戳标记（AK8875）曾恰为污染值子串。断言必须「保存生效校验（盘值=本轮预期）+回显档位校验」双保险。
6. persistent_storage 值=XML 内嵌 JSON 双层转义（&quot; 和 \"），解析要先去实体转义。
7. hdc shell 无 app 私有目录写权限（数据侧修复死路）；卸载清数据按项目规则 AI 不得执行。
