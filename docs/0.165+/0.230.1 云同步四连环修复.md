# 0.230.1 云同步四连环数据安全修复

## 需求分析
0.229.25 SYNC-FLOW 真机测试实锤发现 0.228.0 云同步行模式的四连环数据安全 bug（PENDING 置顶，修前 Pad/PC 双端 force-stop 止血、云端 73 行完好）：

- **Bug A** 重启后全量下拉不完整（PC 首启 24/73、Pad 23 行即停；嫌疑=大 value chunked 行片段不齐）
- **Bug B**（根凶 `ChatModel.ets` flushDeletions）reconcile 末尾无条件 flush，以残缺内存池对账 RDB 全表 → 41 个 del 墓碑自动出生 + 本地物理删行（跨域连坐 node10+tab4+card26，无需用户操作重启即触发）
- **Bug C** 墓碑 updated_at 新于云端行 → 增量下行永不重传 → 本地永久缺
- **Bug D** 墓碑一旦上行成功 → 云端 del 压制 → 全端数据丢失（本次上行未遂=万幸）

## 设计思路（用户定稿修复方向四条 + 实施）
1. **墓碑只准显式删除操作触发，reconcile/flush 自动路径永不写墓碑**：
   - 整体删除 `flushDeletions`（函数 + 6 个调用点）——自动差集对账路径不复存在
   - `recordWordTomb/recordKnowledgeTomb` shim 从「只触发 flush」改为**删除时刻逐 id 写真墓碑**（`writeTombstone`：绕过首拉闸门——显式用户意图任何时刻落库都安全）+ 清本地实体行（含 chunk 残片）
   - 词/卡/夹全部删除路径（单删/批删/夹删/级联删/清空根夹）本就汇入这两个 shim（id 列表带全），零散路径天然覆盖
   - **补齐缺失钩子**：`confirmDeleteBubble`（节点+子树）→ 新 `recordNodeTomb(ids)`；`deleteTab`（Tab+整树节点）→ 新 `recordTabTomb` + `recordNodeTomb`
2. **chunk 缺片标记 pending 绝不流入删除对账**：reconcile 重组 chunk 缺片时——该行不进实体域（现行为）+ 记 pending 计数 + **不开首拉闸门（rowInitDone）**（防残缺态上行旧值覆盖云端新值——同族隐患一并堵死）+ 15s 间隔有界 nudge 重拉（forceCloudSyncNow，≤6 次，成功即重置）
3. **flushDeletions 防呆闸门**：随 ① 整体删除自动路径，③ 的「禁对账」诉求被结构性满足（无自动对账可禁）；rbLog 保留域计数日志供测试断言
4. **修后 SYNC-FLOW 回归**（见验收）
5. **Bug C/D 止血（一次性清洗）**：`initCloudDb` 建表后、activateCloudSync 前，一次性 `DELETE FROM cloud_data WHERE key LIKE 'del:%'`（幂等标记=全新 PersistenceV2 key `tombstone-purge-v1`——0.224.1 教训：旧 key 尾追字段不持久化）。云端完好实体行随完整下拉自愈回本地回池（本地被 Bug B 物理删的行，云端在=拉回=复活进池）；云端若有合法 del 行（早已上传）会重新下行再应用，语义无损
6. **闸门再武装**：`setupCloudDownlink`（每次会话启动）把 `rowInitDone` 重置 false——原实现持久化 true，重启后首拉未完成 flush 即上行，是 Bug A 放大器

## 风险点
- 显式墓碑绕过首拉闸门：显式删除意图落库上传=语义正确（压制的正是用户要删的实体）
- 未挂钩的未知删除路径：表现=复活（安全方向，数据可见可再删），不再有毁灭方向
- del 行无 GC：体积极小，累积无害，GC 留后续迭代
- 本地物理删行后云端实体行会周期性重下行（框架无本地删除语义）——del 行常驻压制，churn 可接受（现状既有）
