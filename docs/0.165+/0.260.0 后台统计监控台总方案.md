## 一、需求定位（用户口述 → 一句话）

**「埋点看板只是埋点的一个数据；后台统计很重要——SP 消耗量、收入、下载量、用户量、停留时间……AGC 开发者中心显示的不全，我们后台必须做一个综合监控台，用于 SP 算法调参 + 商业决策。」**

拆成六大板块：

| 板块 | 回答的问题 | 数据源 |
|---|---|---|
| ① 行为埋点 | 用户在用什么功能 | **已有**（events 表 22 事件） |
| ② SP 消耗与成本 | 每天烧了多少 SP/多少钱、按模型/用户分布 | **自建埋点（新增，核心）** |
| ③ 收入 | 卖了多少钱、兑码/订阅走势 | 兑码记录 + AGC 收入报表导入 |
| ④ 下载/用户规模 | 装机量、激活量、DAU/新增 | 自建激活埋点 + AGC 数据报告导入 |
| ⑤ 停留时长 | 用户每天用多久 | 自建会话事件 |
| ⑥ 告警红线 | 成本失控早知道（V5.0：9.9 档月均成本>5 元→调参） | 看板服务端规则引擎 |

**定位一句话：现有「埋点看板」从单一事件统计，升级为「DAG 运营大脑」——开发者侧的决策仪表盘。**

## 三、华为 AGC 平台能力对照（缺什么补什么）

> ⚠️ 诚实声明：华为开发者文档站为动态页面、本次网页抓取受限；下表基于公开资料+既有控制台实操整理，**实施前逐项在控制台核对**（路径已给）。已实锤结论：AGC 对个人开发者**未开放数据报告/分析数据的公开 REST API**——平台数据只能「控制台手动导出」，这是必须自建看板+做导入功能的根本原因。

| 指标 | AGC 平台有无 | 获取方式 | 我们的策略 |
|---|---|---|---|
| 下载量/安装量/卸载率 | 有（我的应用→数据报告） | 控制台图表+手动导出 CSV | **看板做导入页**，导出文件拖进去画趋势 |
| IAP 订阅收入 | 有（盈利→收入报告） | 控制台导出 | 同上导入 + 现阶段兑码记录人工登记 |
| DAU/新增用户/留存 | 分析服务有，但需集成 Analytics Kit SDK | 控制台 | **不引 SDK**（已有自建埋点，自建 uid 去重即得，免二次合规） |
| 使用时长/单次时长 | 同上需 SDK | 控制台 | **自建 session 事件**（更细：能按页面/场景切） |
| 崩溃/ANR/性能 | 崩溃服务免费（自动采集） | 控制台 | 不自建，控制台看 |
| 评论/评分 | 有 | 控制台（Publishing API 有评论接口，个人可用性待核） | 暂不接，人工记录 |
| 自定义事件 | 分析服务支持 500 个 | 控制台 | 已有自建 track-events，**不重复建设** |

**结论：平台管「分发侧」（下载/收入/崩溃），我们管「应用侧」（行为/SP/时长/用户）。看板=两者汇合处。**

## 四、总体架构（沿用现有三层，只扩不重建）

```
[端侧] TrackUtil（已有，扩事件）
   ├─ sp_consume  ★新：SP 实扣时上报（消耗量/模型/场景/免扣标记）
   ├─ app_session ★新：切后台上报本次前台时长秒数
   ├─ app_first   ★新：首次同意协议后上报（装机激活自建口径）
   └─ p 参数内嵌 u:匿名uid ★新（本地首启生成随机 UUID，零表结构变更）
        ↓ 云函数 track-events → Cloud DB events（e/p/t 不动，u 塞 p JSON）
[看板] 老机器 E:\track-events\dashboard\（已有，升级多 Tab）
   ├─ Tab1 行为埋点（现有页面平移）
   ├─ Tab2 SP 消耗 ★新（日曲线/模型分布/用户TOP/成本换算¥）
   ├─ Tab3 收入 ★新（兑码登记+AGC 报表 CSV 导入）
   ├─ Tab4 规模与时长 ★新（DAU/新增/装机、时长趋势、AGC 下载量导入）
   └─ Tab5 告警 ★新（红线规则引擎，顶部红条）
```

## 五、端侧采集设计（3 个新事件 + 1 个维度）

| 事件 | 触发点 | p 参数 | 埋点位置 |
|---|---|---|---|
| `sp_consume` | AI 回复实扣后（含重生成/未来两段式） | `{u, sp:本次扣点数, m:模型名, sc:场景chat/regen, f:免扣y/n}` | **与 0.259.0 同一收口**：`consumeSiyiSp()` 旁双写（本地 StatDayEntry + 云端 track）——一切新扣点场景自动带上 |
| `app_session` | EntryAbility.onBackground（已有 flush 链路天然出口） | `{u, secs:本次前台秒数}` | 前台时长累计，切后台必报 |
| `app_first` | 用户协议同意门禁通过后（一次性） | `{u}` | 自建装机激活口径，与 AGC 下载量互为印证 |

**uid 方案**：首启生成随机 UUID（如 `d3f9a2…`，12 位截断）存 preferences；**不含任何个人身份信息**（非 OAID/非华为账号），纯设备内随机数。塞进 p 的 JSON——**events 表零结构变更**（云端表 e/p/t 不动，看板端解析 p.u 即得用户维度）。

**口径纪律**：埋点字典同步登记（项目既有铁律）；SP 相关事件名对用户不可见（防反推铁律只约束 app 内界面，埋点事件名不在用户可见范围）。

## 六、看板升级方案（老机器 dashboard 扩展）

1. **Tab2 SP 消耗**：日/周/月消耗曲线、按模型分布饼图、匿名 uid TOP 榜、**成本换算 ¥**（换算系数放看板 `config.json`——SP 算法调参时改配置不改代码；app 内禁 ¥-SP 换算，看板是开发者内部工具不受限）。
2. **Tab3 收入**：现阶段=兑码记录表单（码/档位/日期/渠道人工一条条录或批量贴）；上架后=AGC 收入报告导出 CSV 拖入解析，画月收入走势 + 消耗成本对冲（毛利视图）。
3. **Tab4 规模与时长**：DAU（当日事件按 u 去重）、新增（u 首见日期）、装机激活（app_first 计数）、人均时长（session 聚合）；AGC 下载量 CSV 导入叠加对照。
4. **Tab5 告警**：服务端每日定时跑规则（V5.0 红线：9.9 档月均真实成本>5 元；可扩展：DAU 连跌 N 天、免扣账号成本异常等），超线=看板顶部红条常驻+最近触发记录。
5. **安全加固（顺手）**：8766 目前局域网裸奔，上成本/收入数据后加简单访问口令（Basic Auth 或 URL token）。
6. **数据量治理**：当前量小（/api/data 拉 1 万条够用）；DAU 上千后 events 表超拉取上限——二期做**服务端日汇总表**（云函数或看板端日终聚合成 metrics 行，明细滚动清理）。

## 七、合规红线（不越界）

- 行为/SP/时长埋点继续走「体验改进计划」隐私开关（默认关，用户拍板过的合规决定，不因运营需求反转）。
- `app_first` 激活计数是否随隐私开关（保守）还是随协议同意（积极、需隐私政策披露一句）——见选择题 Q5。
- uid 为本地随机数、无个人身份属性；隐私政策中「我们收集什么」章节按最终拍板档位补充披露。
- 看板含成本/收入数据：仅内网+口令，绝不公网暴露。

## 九、分期建议（等当前 APP 开发线收官后启动）

- **一期（核心，约 1 个迭代）**：端侧 3 事件 + uid + 看板 Tab2（SP 消耗/成本）/Tab4（DAU/时长）+ 口令加固。→ 直接服务「SP 算法调参」最急需求。
- **二期（商业完善）**：Tab3 收入（兑码登记+CSV 导入）+ Tab5 告警引擎 + 服务端日汇总表 + 老机器通知。
- **上架后**：AGC 真实收入报表导入、留存分析、（评估）华为 Analytics Kit 双埋点。

## 十、验收标准（实施后）

1. AI 对话一次 → 云数据库 events 出现 sp_consume 行，p 含 u/sp/m/sc/f 且数值=本次实扣。
2. 免扣账号（Lv8）对话 → 同样出现 sp_consume 行、f:y。
3. App 前台使用 10 分钟切后台 → app_session 行 secs≈600（±10s）。
4. 全新安装+同意协议 → app_first 恰好 1 行。
5. 看板 Tab2 日消耗曲线与端内统计页（0.259.0 第五卡）当日值一致（双口径互验）。
6. 拖入 AGC 下载量 CSV → Tab4 画出趋势且与自建激活数并列展示。
7. 看板无口令访问被拒。

## 十一、发散种子（跨领域对照，供联想）

- **Stripe Dashboard 模式**：收入+成本+流失一屏——Tab2/Tab3 的「毛利视图」即此思路，个人开发者也能有上市公司级仪表盘。
- **Cloudflare Analytics 模式**：不存 PII 只存聚合——本方案 uid 匿名化同款哲学，合规成本最低。
- **北极星指标建议**：别只看 DAU，看「单位学习产出的 SP 成本」（消耗 SP ÷ 完成复习数）——健康值稳定=算法合理；恶化=该调参数了。这比单纯成本红线更早发现问题。
