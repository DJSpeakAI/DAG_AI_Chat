## 四、性格测试重做机制（本轮新增拍板）

**动机（用户口径）**：性格测试唯一目的是帮 AI 更好回答；有人第一遍随便做，必须给改错机会。

1. **重做入口迁全局设置**：GSD「AI 偏好」区尾部加一行「重新做性格测试」（仅做过一次的人可见），用户后续统一规划 GSD 时再挪位（先随便放）。
2. **画布左下角信号灯条件改造**：显示条件从 `!quizStore.done` 改为 `!quizStore.everDone`（everDone=尾部追加新字段「曾经完成过」）——首次完成后信号灯永久消失，重做不再唤醒信号灯；未做过的新用户信号灯引导照旧。
3. **重做数据操作**（全部为字段覆写，Schema 铁律合规，不删不改既有字段）：
   - answers/choiceAnswers/done/profileWritten 清零重置 → 重新可答、评阅重跑；
   - **everDone 保持 true**（信号灯不复活）、**claimed 保留**——重做答题时 quizNodeReached 最高 3 ≤ claimed，claimQuizSp 天然算出 0，**SP 不再发（防刷死锁，零额外代码）**；
   - 评阅画像走 appendObservation 既有 supersededBy 演变链（新画像行取代旧行，ProfileModel 原生支持，只增不删）。
4. **任务面板第 7 条判定** = everDone（曾完成即✓，重做期间保持✓不回退）。

## 五、SP 云服务门槛与挂账补发（本轮新增拍板，核心）

**用户口径**：所有 SP 的消耗与增加都必须开通云功能后才会有；没开通=点任务入口弹窗提示开通云服务；但功能本身照用（背单词当然可以），后台检测照记信号，有信号自动打勾该条。

1. **「已开通云服务」定义**：华为账号已登录 && 云同步开关已开（复用 HuaweiAccountUtil requireLoginForCloud 守卫族 + cloudSwitch 状态，0.248 先例）。
2. **发放守卫**：grantBonusSp 收口（嘉奖发放统一入口：性格测试节点+新手任务+完赛奖）前置云服务检查：
   - 已开通 → 照常发放（嘉奖池+云上行+sp_grant 埋点三件套）+ 弹「+N SP」窗；
   - 未开通 → 不发放，任务照常打勾，状态=「已完成·开通云服务后到账」。
3. **挂账补发**：开通云服务那一刻（登录成功/云同步开启成功钩子）自动结算——对账本地任务 done 集 vs 云行 granted 集，差集一次性补发（一笔汇总弹窗「新手任务奖励 N SP 已到账」），随后转入即时发放模式。
4. **完成信号本地真相**：未开通期间信号记本地 rookie-tasks-v1（云同步没开本地就是唯一真相；开通后随 cfg:siyi-points 行上行合并，多端收敛）。
5. **检测不设门槛**：7 处业务检测点无条件执行（用户背单词/划词/发消息完全不受云服务影响），只发 SP 受限——功能体验与资产结算分离。
6. **门槛范围定稿（二轮拍板）**：只收口 grantBonusSp 族=性格测试节点+新手任务+完赛奖；**签到 doSignIn 零改动**（「签到随便他去，他每天都要签到的」——签到保持现状无门槛）；IAP 充值链路天然需华为账号，不加改。

## 九、风险点

1. **grantBonusSp 加守卫的波及面**：性格测试节点发放也走它——未开通用户做性格测试时节点 SP 也会挂账（行为一致化，属预期；验收用例覆盖）。
2. **挂账结算时机**：登录/开云同步的回调链要可靠（requireLoginForCloud 成功路径 + cloudSwitch.enabled 翻 true 的 @Monitor，0.229.24 同族教训：permGranted 快照滞后，此处用 @Monitor 重查而非快照）。
3. **重做态与断点续做互斥**：重做重置后 quizAnswerTotal 归零，PersonalityQuizDialog 断点续做逻辑天然从第 1 题开始（无需特判，但需断言覆盖）。
4. ChatModel 2959 行中枢：按 AOCI 行号区段精读，只动尾部追加/行桥/grantBonusSp 三区段。
5. 弹窗时机打断：司枢/复习场景延后弹（§七.5）。
6. 角标与信号灯并存：右上角任务+左下角信号灯（仅未做过性格测试者可见），首版并存。

## 十、验收标准

1. 新装机打开画布：右上角任务入口 + 角标 7；**未开通云服务点入口=弹窗引导开通、不进面板**。
2. 未开通状态下完成任意任务（如背单词首次复习成功）：任务静默打勾（无 SP 弹窗）；开通云服务后自动收到汇总补发弹窗、SP 到账。
3. 已开通用户逐条完成：每条瞬间/结束时弹「+N SP」、嘉奖池立增、面板打勾（不按顺序，做完哪个勾哪个）。
4. 性格测试条目：进度 x/15 推进；做完打勾；画布信号灯永久消失；GSD 出现「重新做性格测试」入口。
5. 重做性格测试：15 题重答+评阅刷新画像；**SP 不再发**（节点与任务奖都不重发）；任务面板第 7 条保持✓。
6. 7 条全亮：完赛弹窗+烟花+2 万到账；右上角入口消失。
7. 双端同账号：任务状态与已领标记云同步一致、重复操作不重复发。

## 十二、附带核实：签到「每日首开自动弹」现状（唯一余项，待拍板）

用户口径：「自然时间 0 点后第 1 次打开 APP，未签到则自然弹出签到口——好像现在就是这样，你可以看一下」。

**核实结论（2026-10-22 代码实锤）：现状不是这样**。签到弹窗现有触发点只有两个：
- `maybeShowSignInGuide()`（ChatModel.ets:1834）——登录成功后的**首登引导**，guideShown 只弹一次，非每日；
- AppSideBar.ets:988——用户**手动点**边栏签到入口（红点驱动）。

即目前**没有**「每天首次打开 APP 且当日未签到 → 自动弹签到窗」的机制。

- **选项 A（搭车本迭代，推荐）**：EntryAbility onForeground/Index 启动链加一处「当日未签到 && 今日未弹过 → 弹签到窗」（isSignedToday 判定+每日去重标志，与 0.256.0 签到体系同源，约 20 行）。
- **选项 B（不做）**：维持手动签到入口+红点提醒现状。

拍板 A 则列入本迭代改动清单（EntryAbility.ets 1 处局部）；拍板 B 则本方案零余项、直接开工。
