# 0.132 流式回复卡「AI正在回复中」bug 修复方案

> 状态：**已交付**（2026-10-02 用户批准全量实施，同日编译+真机验证通过）
> 日期：2026-10-02
> 前置：0.131（全项目清理）交付后用户测试发现

---

## 一、问题现象

- 发送消息后，AI 回复气泡**永远停留在「AI正在回复中，请稍候...」**
- 但同一条消息的 **token 统计正常显示**（如「输入 304 · 输出 137」）
- **重启 app 后，同一条消息显示完整回复内容**（数据没有丢）

用户截图证据：两条消息分别显示「输入 37 · 输出 99」「输入 60 · 输出 1693」，全部卡占位。

## 二、排查过程（真机实测，非推测）

设备：Wi-Fi 真机 192.168.2.9:35425，bundle `com.example.dag_ai_chat`

1. **实时复现**：进入对话气泡，发送「用一句话介绍你自己」，发送后 2~4 秒抓取控件树（uitest dumpLayout）：
   - AI 气泡 Text = `"AI正在回复中，请稍候..."`
   - 同一消息 token Text = `"输入 304 · 输出 137"`（**token 写入发生在 onDone，说明流已正常结束**）
2. **重启验证**：重启 app 后同一条消息显示完整 AI 回复（20 行文本完整）——**持久化数据完整，网络接收/解析/拼接全链路正常**
3. **结论**：bug 在 **UI 渲染层**，不在网络层、SSE 解析层、数据层

## 三、根因（已实锤）

`ChatPage.ets` 第 538/591 行，AI 消息的 Markdown 分段渲染：

```typescript
ForEach(this.parseMarkdown(msg.content), (seg: MdSegment, idx: number) => {
  ... Text(seg.content) ...
}, (seg: MdSegment, idx: number) => `${idx}_${seg.type}`)   // ← 问题在这
```

完整因果链：

1. 流式期间，纯文本回复**始终只产生 1 个 `type=0` 段** → key 恒为 `'0_0'`
2. ArkUI ForEach 机制：**key 不变 → item 复用 → itemGenerator 不重新执行**
3. `MdSegment` 是普通 class（非 `@ObservedV2`），复用的 item 里 `Text(seg.content)` 绑定的是**旧对象的旧值** → 永不更新
4. 首次渲染时 content 是占位文字 → **屏幕永远显示「AI正在回复中，请稍候...」**
5. 对比：token 统计是 `if (msg.outputTokens > 0)` —— `outputTokens` 是 `@Trace`，0→137 触发**结构变化**（if 分支新建 Text）→ 正常显示
6. 对比：用户消息 `Text(msg.content)` 直接绑定 `@Trace` → 正常刷新（用户消息不受影响）

**引入时间：0.121**（引入 parseMarkdown 分段渲染时埋下），与 0.131 改动无关（时间巧合）。0.121~0.130 期间未暴露，推测此前测试回复多为多段内容（含代码块），新增段落的 key 会新建 item，仅首段卡旧内容不易察觉；纯文本长回复则 100% 复现。

## 四、修复方案（4 项）

### 修复 1（核心·必改）：keyGenerator 纳入内容尺寸

```typescript
// 旧
(seg: MdSegment, idx: number) => `${idx}_${seg.type}`
// 新
(seg: MdSegment, idx: number) => `${idx}_${seg.type}_${seg.content.length}_${seg.header.length}_${seg.rows.length}`
```

- 原理：流式追加 → `content.length` 单调递增 → key 变化 → item 重建 → 显示最新内容
- 表格段（type=2）流式成型时 `header/rows` 增长同样触发重建
- 性能：流式期间每个 chunk 重建当前段的 Text；流式中段数通常 1~3 个，纯 Text 重建开销可忽略；`parseMarkdown` 全文重解析（O(n)，n≈回复长度）每 chunk 一次，500 字符级回复开销微小
- **改动量：1 行**

### 修复 2（防御·强烈建议）：SSE 字节级缓冲，杜绝 UTF-8 切断

`ApiClient.ets` `dataReceive` 回调现状：

```typescript
const dataStr = buffer.from(data).toString();  // ← TCP chunk 边界切在多字节字符中间时，产生 U+FFFD 乱码
sseBuffer += dataStr;                          // ← 乱码已固化进字符串，remainder 机制无法恢复
```

中文回复 + 多 chunk 传输时，chunk 边界落在汉字中间的概率不低 → 该行 JSON.parse 永久失败 → **概率性内容丢失**（本次实测未触发，属同链路确定性缺陷）。

修复：**字节级累积，只在完整行边界（`\n` 字节）处解码**：

```typescript
let pendingBytes: Uint8Array = new Uint8Array(0);

httpRequest.on('dataReceive', (data: ArrayBuffer) => {
  // 1. 拼接：pendingBytes + 新字节
  const incoming = new Uint8Array(data);
  const merged = new Uint8Array(pendingBytes.length + incoming.length);
  merged.set(pendingBytes);
  merged.set(incoming, pendingBytes.length);
  // 2. 找最后一个 \n（0x0A），只解码完整行部分
  let lastNl = -1;
  for (let i = merged.length - 1; i >= 0; i--) {
    if (merged[i] === 0x0A) { lastNl = i; break; }
  }
  if (lastNl >= 0) {
    const complete = merged.subarray(0, lastNl + 1);
    sseBuffer += buffer.from(complete.buffer, complete.byteOffset, complete.byteLength).toString();
    pendingBytes = merged.subarray(lastNl + 1);   // 不完整尾部留待下个 chunk
  } else {
    pendingBytes = merged;                        // 无完整行，全部保留
  }
  // 3. 解析 + 回调（原逻辑不变）
  ...
});
```

- 原理：SSE 协议保证事件以 `\n` 结尾；被切断的多字节字符必然位于最后一个 `\n` 之后，等下个 chunk 拼齐后才解码，**永不产生乱码**
- `dataEnd` 兜底：把 `pendingBytes` 剩余字节全部解码后走原有 remainder 解析
- `parseSSEChunk` 及 remainder 机制保持不变（兼容无损）

### 修复 3（体验·用户已确认）：深度思考状态提示

火山方舟 Seed 系列为深度思考模型（不传 `thinking` 参数时可能默认开启），思考内容走 `delta.reasoning_content` 字段，当前解析器只认 `delta.content`。本次实测 seed-2.1-lite 未走思考路径（防御性适配，避免未来切模型踩坑）。

改动：
1. `ApiClient.ets`：`SSEResponseDelta` 增加 `reasoning_content?: string`；`parseSSEChunk` 提取 reasoning 到 `SSEResult.reasonings`；`streamChat` 新增**可选**第 6 参数 `onReasoning?: (text: string) => void`（不传则忽略，现有调用零影响）
2. `ChatPage.ets` `sendMessage`：传入 `onReasoning`，把占位文字从「AI正在回复中，请稍候...」切换为「AI 正在深度思考中...」（不追加进 content，不参与持久化和上下文）
3. 占位文字判断兼容两态：定义常量 `PLACEHOLDER_LOADING` / `PLACEHOLDER_THINKING`，`onChunk` 清占位、`buildBranchMessageList` 过滤占位、修复 4 兜底判断，统一兼容两个占位值

### 修复 4（兜底）：空回复提示

`sendMessage` 的 `onDone` 里：若 `aiMsg.content` 仍为占位文字（任何未预见情况导致零内容），替换为「（AI 未返回文本内容，请重试或更换模型）」——**杜绝任何场景下永久卡占位**。
