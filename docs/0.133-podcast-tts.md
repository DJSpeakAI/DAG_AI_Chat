> **状态：待审批**
> 日期：2026-10-02
> 前置版本：0.132（流式渲染修复，已交付，见 docs/0.132-bugfix.md）
> 方案来源：用户与豆包讨论的方案（豆包侧编号 0.114），经本项目审查修订后定稿

## 一、需求背景

在现有气泡树 AI 对话（DAG_AI_Chat）基础上新增两个能力：

1. **下拉发送模式**：发送按钮左侧新增下拉选择，两种模式：
   - **正常对话**（默认）：现有行为完全不变
   - **播客模式**：发送时在消息末尾追加一条播客系统 prompt，让 AI 输出口语化、适合朗读的文本（无代码块/表格/列表/markdown 标记）
2. **AI 消息语音朗读**：每条 AI 消息下方新增喇叭图标，点击后将该消息文本送 TTS（文本转语音）合成并播放；再次点击停止

两次独立请求的架构：**LLM 生成文本 → TTS 合成音频 → 播放**，即朗读是手动触发的第二次请求，不在对话请求里合成音频。

## 三、功能设计

### 3.1 下拉发送模式（ChatPage 输入区）

- 发送按钮左侧新增一个模式下拉按钮，显示当前模式图标 + ▾：
  - 正常对话：`💬▾`
  - 播客模式：`🎙▾`
- 点击弹出选项面板（复用设置页下拉面板的交互模式）：
  - `💬 正常对话`（默认选中）
  - `🎙 播客模式`
- 选中后按钮图标立即切换，**只对下一次发送生效**，不影响历史消息

### 3.2 播客模式

播客系统 prompt 常量（原文，追加在发给 LLM 的消息列表末尾）：

```
你的回答会用于语音朗读，请输出自然流畅的中文口语段落。禁止输出代码块、表格、列表、markdown 标记、特殊符号。只用连续自然的文字，适合耳朵收听。
```

插入位置：`sendMessage()` 内拿到 `messagesToSend`（链路回溯+压缩后的消息列表）**之后**追加一条 system 消息。**不改 `buildBranchMessageList()`**——链路回溯、摘要压缩逻辑零改动，播客 prompt 不参与持久化、不进入后续上下文。

标记：播客模式发送时，本次的 userMsg 和 aiMsg 都置 `isPodcastMode = true`（记录这次交互的模式，为后续迭代「播客消息视觉标记」打基础；MVP 阶段该字段仅存储，不影响 UI）。

### 3.3 喇叭朗读（AI 消息）

每条 AI 消息的 token 统计行旁新增喇叭图标，**三态**：

| 状态 | 图标 | 行为 |
|------|------|------|
| 空闲 | 🔈 | 点击 → 请求 TTS 并播放 |
| 加载中 | ⏳ | TTS 请求进行中，点击无效（防重复请求） |
| 播放中 | 🔊 | 点击 → 停止播放，恢复 🔈 |

规则：
- **播新停旧**：全局同一时刻只有一个播放源。播放 A 时点 B 的喇叭 → A 立即停止、B 开始播放
- **占位态不可读**：消息内容还是「AI正在回复中/深度思考中」占位文字时点喇叭 → toast「AI 回复完成后才能朗读」；流式已开始（占位已清除）的消息可朗读当前已收到的部分
- **删除即停**：朗读中删除该条消息 → 停止播放
- **退页即停**：退出对话页（返回画布/切气泡）→ 停止播放
- **失败提示**：TTS 请求失败 → toast 轻提示错误，喇叭恢复空闲态
- 历史普通消息（非播客模式）同样可点喇叭朗读（含表格/代码会原样读出，MVP 不做 Markdown 剥离）

### 3.4 设置页音频模型配置（SettingsPage）

新增「音频模型」配置区，位于现有 Model 配置之后：

- **音频模型下拉**：预置列表（见 4.6），交互照抄现有 Model 下拉（点击行 → 展开面板 → 选中高亮）
- **可编辑**：下拉下方加 TextInput，显示当前选中的模型 ID，可手动输入自定义 ID（覆盖下拉选择）
- **音频 Endpoint 输入框**：照抄现有 Endpoint 输入框模式，默认值见 4.2
- 保存按钮统一写入 `apiConfig.audioModel` / `apiConfig.audioEndpoint`（与现有 apiKey/endpoint/model 一起保存）

### 4.1 数据模型（ChatModel.ets）

**① ChatMessage 新增 `isPodcastMode`**

```typescript
@ObservedV2
export class ChatMessage {

              outputTokens = 0, isPodcastMode = false) { ... } // 可选参数带默认值，现有 6 处调用点不破坏
}
```

**② ApiConfig 新增音频配置两个字段**

```typescript
@ObservedV2
export class ApiConfig {
  @Trace apiKey: string = '';
  @Trace endpoint: string = 'https://ark.cn-beijing.volces.com/api/v3/chat/completions';
  @Trace model: string = 'doubao-seed-2-1-lite-260915';
  @Trace audioModel: string = 'doubao-tts-anchor-65-241005';    // ★ 0.133：音频模型（预置公开 ID，设置页可改）

```

PersistenceV2 自动持久化新增字段，旧版本数据加载时取默认值，无需迁移。

**③ 序列化兼容（关键，防旧数据丢失）**

- `SerializedMessage` 接口新增 `isPodcastMode?: boolean`（可选字段）
- `serializeBubbleTree()`：写入 `msg.isPodcastMode`
- `deserializeBubbleTree()`：读取 `msg.isPodcastMode ?? false`（旧数据无此字段 → 自动 false，不报错）

> 与 0.117 引入 `historySummary?` 的兼容手法一致。

### 4.2 TTS 请求（ApiClient.ets）

新增 `synthesizeTTS()` 函数——**非流式**一次性 HTTP 请求（`http.createHttp().request()`），与现有 `streamChat()` 的 SSE 流式完全独立：

```typescript
// 文本 → 语音：成功回调 base64 音频（或二进制，按协议），失败回调错误信息
export function synthesizeTTS(
  text: string,
  config: ApiConfig,
  onDone: (audioData: string) => void,
  onError: (error: string) => void
): StreamController // 复用 cancel 模式，停止朗读时取消进行中的请求
```

**TTS 协议（两条候选路径，实施时真机联调核验，见第九节风险）**：

- **路径 A（首选，方舟 v3，OpenAI TTS 兼容格式）**——用户已有方舟 API Key，零额外配置：
  ```
  POST https://ark.cn-beijing.volces.com/api/v3/audio/speech
  Authorization: Bearer {方舟APIKey}
  Content-Type: application/json
  {
    "model": "{audioModel}",
    "input": "{text}",
    "voice": "{音色ID}",
    "response_format": "mp3"
  }
  响应：mp3 音频二进制流
  ```
- **路径 B（备选，火山引擎语音技术 2.0 接口）**——若方舟不支持 audio/speech 端点则切换：
  ```
  POST https://openspeech.bytedance.com/api/v1/tts
  Authorization: Bearer; {access_token}    ← 注意：Bearer 后带分号，官方特殊格式
  {
    "app":    { "appid": "{appid}", "token": "{token}", "cluster": "volcano_tts" },
    "user":   { "uid": "dag_ai_chat" },
    "audio":  { "voice_type": "{audioModel}", "encoding": "mp3", "speed_ratio": 1.0 },
    "request":{ "reqid": "{uuid}", "text": "{text}", "text_type": "plain", "operation": "query" }
  }
  响应：JSON，code=3000 成功，data 字段为 base64 编码的 mp3
  ```

两条路径的差异（鉴权头、请求体、响应格式）全部封装在 `synthesizeTTS()` 单函数内，切换路径只改这一个函数，不影响其他代码。

### 4.3 长文本分段（ChatPage.ets）

TTS 单次请求有文本长度上限（官方约 340 汉字）。新增纯函数：

```typescript
splitTextForTTS(text: string): string[]
```

切分规则：
1. 按句末标点（。？！；）和换行符切句
2. 累积句子到接近 340 字符为一段
3. 单句超 340 字符 → 按逗号（，、）再切
4. 仍超 → 硬切

播客模式的回复天然是连续口语段落，此规则可保证段落在自然语义边界断开，听感不突兀。

### 4.4 播放器封装（ChatPage.ets）

**技术选型：AVPlayer**（`@ohos.multimedia.media`）。不用 SoundPool——它面向短音频（<20 秒提示音），340 字语音段可达 60 秒以上，AVPlayer 才稳。

**播放路径**：

```
TTS 响应（base64/二进制）→ 解码 → 写入 cacheDir 临时文件 tts_{messageId}_{segIndex}.mp3
→ AVPlayer url 设为 fd://{fd} → prepare → play
→ 播完（stateChange → completed）→ 删临时文件 → 队列取下一段
→ 全部播完 → release 播放器 + 清状态
```

**生命周期纪律**：每次播放新建 AVPlayer 实例；停止/完成即 `release()` + 删除临时文件，杜绝泄漏。

**队列播放状态**（ChatPage 组件内）：

```typescript
@Local playingMessageId: string = '';     // 正在播放的消息（驱动喇叭图标三态）
@Local ttsLoadingMessageId: string = '';  // TTS 请求中的消息（⏳ 态，防重复点击）
private ttsSegments: string[] = [];       // 分段队列
private ttsSegmentIndex: number = 0;      // 当前播放到第几段
private ttsRequestController: StreamController | null = null; // 进行中的 TTS 请求
private avPlayer: media.AVPlayer | null = null;
```

**播新停旧**：`startTTS(msg)` 入口先调 `stopTTS()`（清队列 + 取消请求 + release 播放器），再启动新消息的合成。

**停止触发点**（全部收敛到 `stopTTS()` 一个函数）：
1. 播放中再点同一喇叭
2. 播放中点另一条消息的喇叭（播新停旧）
3. `deleteMessage()` 删除正在播放的消息
4. `aboutToDisappear()`（退出对话页；现有交互下切气泡必经 pop，一个钩子覆盖「退页 + 切气泡」两种情况）

## 六、边界与约束

1. 模式切换只对**下一次发送**生效，不追溯历史消息
2. 播客 prompt 不持久化、不进入后续对话上下文（只在请求时临时追加）
3. `isPodcastMode` MVP 阶段仅存储标记，不做视觉区分（后续迭代）
4. LLM 与 TTS **共用 API Key**（路径 A），但 **Endpoint 相互独立**（endpoint / audioEndpoint 各配各的）
5. 朗读是手动触发，播客模式回复完成后**不自动朗读**（后续迭代可加）
6. 旧版本持久化数据（无 isPodcastMode 字段）加载后自动补 false，不报错、不丢失
7. TTS 失败不影响对话功能本身（对话与朗读完全解耦，失败仅 toast）

- Markdown 剥离（代码块/表格消息会原样读出符号）
- 播客模式回复完成自动朗读

## 九、风险与开放问题

| # | 风险 | 应对 |
|---|------|------|
| 1 | **TTS 协议细节未实锤**：方舟是否支持 `/api/v3/audio/speech` 端点、doubao-tts 模型的准确调用格式，官方文档为 SPA 页面无法程序化抓取 | 实施第一步先真机联调核验：先按路径 A 发请求，按实际响应（成功/404/鉴权错误）切换路径 B；协议差异全部封装在 synthesizeTTS() 单函数内，切换成本可控 |

| 4 | TTS 单次文本上限（约 340 汉字）为经验值 | 分段阈值做成常量，联调时按官方文档微调 |
| 5 | AVPlayer 状态机时序（prepare 异步、release 时机） | 严格按官方状态机图实现：idle → initialized → prepared → playing → completed → released；所有状态跃迁在 stateChange 回调里处理 |
