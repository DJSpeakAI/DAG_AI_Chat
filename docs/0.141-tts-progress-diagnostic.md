# 0.141 TTS 过程消息诊断增强

## 背景

0.140（音频 Key 独立字段 + 设置页滚动修复）真机验证后，用户反馈：设置页已正常（可滚动、可保存），但点喇叭朗读后**沙漏一直转**——既不出声，也没有新的失败调试消息。

由于本机工具无法稳定抓取真机日志（多次尝试中断），改用用户提议的方案：**在代码里加过程性反馈消息**，让流水线每走一步都在对话里发一条 [TTS过程] 消息，用户截图回传即可精确定位卡点。

## 三大嫌疑

| 嫌疑 | 描述 | 可能性 |
|------|------|--------|
| A. HTTP 流式响应挂起 | openspeech unidirectional 是 Chunked 单向流，若服务器推完音频不主动结束流，http.request() 的 then 永远不触发 | 最可疑 |
| B. 播放环节卡住 | 音频已到达，但写临时文件 / 创建播放器 / prepared 状态某环节失败 | 次之 |
| C. 请求没发出 | 基本排除——那会立刻触发 onError 的调试消息 | 基本排除 |

## 方案：全流水线 [TTS过程] 直播

给 synthesizeTTS 加可选参数 onProgress，在请求/响应/解析三个节点回调；ChatPage 新增 addTTSProgressMessage 方法把过程消息插入当前气泡（复用 ChatMessage + 持久化，与 [TTS调试] 同机制）；播放链路（写文件、播放器就绪）也各加一条。

## 改动明细（8 处）

### ApiClient.ets（4 处）

1. **synthesizeTTS 签名**：加第 5 个可选参数 `onProgress?: (info: string) => void`（★ 0.141-DEBUG）
2. **catch 之后**：`请求已发出: URL=..., Key长度=N, 等待服务器响应...`（request() 调用后同步触发）
3. **then 回调**：`收到响应: HTTP N, 响应体 N 字符, 内容: 前200字符`
4. **解析完成**：`N 段 base64 拼接 N 字节, base64 长度 N`

### ChatPage.ets（4 处）

5. **新增 addTTSProgressMessage 方法**：[TTS过程] 前缀消息插入当前气泡并持久化
6. **requestNextSegment**：synthesizeTTS 调用传第 5 参数（包装 addTTSProgressMessage，带段号前缀）；onDone 里加 `第 N 段音频已到达（base64 长度 N），进入播放队列`
7. **playSegment**：写文件后加 `第 N 段临时文件写入完成（N 字节），创建播放器...`
8. **stateChange prepared**：`第 N 段播放器就绪，开始播放`

## 过程消息时序（每段）

```
[TTS过程] 请求已发出: URL=..., Key长度=N, 等待服务器响应...
[TTS过程] 收到响应: HTTP 200, 响应体 N 字符, 内容: ...
[TTS过程] 解析完成: N 段 base64 拼接 N 字节, base64 长度 N
[TTS过程] 第 N 段音频已到达（base64 长度 N），进入播放队列
[TTS过程] 第 N 段临时文件写入完成（N 字节），创建播放器...
[TTS过程] 第 N 段播放器就绪，开始播放
```

## 定位分支（用户测试后按停点判断）

| 停在哪 | 结论 | 下一步 |
|--------|------|--------|
| 只有「请求已发出」，无「收到响应」 | HTTP 挂起实锤（嫌疑 A） | 改流式接收：http.createHttp 的 on('headersReceive')/on('dataReceive')/on('dataEnd') 事件，收到数据就处理，不等流结束 |
| 有「收到响应」，无「解析完成」 | 解析卡住 | 看响应内容前 200 字符，修正正则 |
| 有「音频已到达」，无「文件写入」 | onDone 到播放链路断 | 检查 onDone 回调与播放队列衔接 |
| 有「播放器就绪」，没声音 | 播放器问题 | 检查 AVPlayer 状态机与音频文件格式 |
