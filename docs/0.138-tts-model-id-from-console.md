## 二、404 根因分析（证据链收口）

### 实测证据（两次独立真机实测，结论一致）

| 时间 | 版本 | model | 结果 |
|---|---|---|---|
| 0.134 | doubao-tts | POST 端点 | **404，无 body，180ms** |
| 0.137 | doubao-tts | POST 端点 | **404，无 body**（本次截图第二条） |

辅助证据：GET 该端点返回 **401**（端点本身存在，鉴权层拦截）→ 404 不是「路径写错」，而是**服务器对 `model: doubao-tts` 这个值的明确回答：模型不存在或未开通**。

### 开源证据的重新审视（推翻 0.134 的依赖）

0.134 当时采用 `doubao-tts` 的依据是 Sourcegraph 开源实证，本次重新审视发现证据力不足：

1. **labring/aiproxy 是 API 网关项目**——它的「Doubao-tts AudioSpeech 适配器」是网关自己实现的转发层，`doubao-tts` 是**网关内部标识**，不等于直连方舟时可用的模型 ID。
2. **clipforge / Mora 的 tts-presets.ts 只是预设配置文件**——无法证明作者实际用方舟账号跑通过；配置可能过时或面向中转服务。
3. **`doubao-tts-241215` 已被证伪**——Bing 全网精确匹配零结果（0.134 文档里的猜测 ID）。

### 结论

`doubao-tts` 这个 ID 在**用户的方舟账号**上不可用（不存在或未开通）。继续猜 ID = 每猜错一次浪费用户一轮真机测试 + 一轮对话。**唯一权威来源：用户方舟控制台里「语音合成-2.0」的实际 Model ID**——0.136/0.137 方案三分支的第一分支预案，现在正式走到这一步。

## 三、修复方案（两步走，第一步零代码）

### 第一步：用户从控制台获取真实模型 ID（唯一需要你做的）

1. 电脑浏览器登录 **火山方舟控制台**：https://console.volcengine.com/ark
2. 进入 **「模型广场」**（或「开通管理」），找到 **「语音合成-2.0」**（你 Key 权限页已勾选的模型）
3. 复制它的 **Model ID**（形如 `doubao-tts-xxxx-xxxxxx` 的具体版本 ID，**不是**商品名）
4. 顺手确认该模型状态为 **「已开通」**（若显示「未开通/需开通」，点开通——权限勾选 ≠ 模型开通，0.134 风险表预判过这一点）
5. 把 Model ID 发给我（若控制台里同时有「语音合成」1.0 版本且已开通，也可以一并发出，多一个备选）

> 补充：如果你在控制台创建过「推理接入点」（ep- 开头的 ID），ep-xxx 也可以直接用——方舟的 model 字段两种都接受。

### 第二步（快速验证路，零代码改动）：设置页直改

拿到 ID 后**不用等我改代码**，最快验证路径：

1. App 设置页 → 「音频模型」TextInput → 把 ID 直接填进去 → 保存
2. 对话页点喇叭 → 看结果：
   - **HTTP 200 出声** 🎉 → 验证通过，走第四节数据固化收尾
   - **4xx + 响应体有 JSON 错误信息** → 把调试消息截图给我，按错误信息直改（voice 格式等）
   - **仍 404** → 截图给我（说明该 ID 也不可用，需检查「开通」状态或区域）

### 第三步（代码固化，验证出声后我来做）

- `ChatModel.ets`：`audioModel` 默认值 `doubao-tts` → 验证通过的真实 ID（一处小改）

- 剔除 ★ 0.136-DEBUG 调试功能（addTTSDebugMessage、buildMessages 过滤、TTSDebugInfo 接口、onError debug 参数链路）

## 五、风险与兜底

| 风险 | 说明 | 兜底 |
|---|---|---|
| 控制台显示的 ID 就是 doubao-tts | 理论上可能（说明 404 另有原因：区域/计费） | 检查控制台「开通管理」状态与计费方式；调试消息会显示新错误细节 |
| 语音合成-2.0 未开通 | 权限勾选 ≠ 开通 | 控制台一键开通（该模型有免费额度可能性高） |
